### 1.2 モジュール依存関係

```
main.c
  └─ debugger.c ── breakpoints.c
                 ── commands.c ── cmdline_parser.tab.c（cmdline_parser.y 生成）
                                └─ cmdline_lexer.yy.c（cmdline_lexer.l 生成）
                 ── registers.c
                 ── symbols.c ── disasm.c
                              └─ expr.c ── expr_parser.tab.c（expr_parser.y 生成）
                                        └─ expr_lexer.yy.c（expr_lexer.l 生成）
                 ── leakcheck.c ── symbols.c
                 ── threads.c（v2.0）
                 ── watchpoints.c ── threads.c（v2.0、全スレッド適用のため）
                 ── processes.c（v3.0）

commands.c ── breakpoints.c / registers.c / memory.c / symbols.c / expr.c / leakcheck.c / watchpoints.c / threads.c（v2.0）/ processes.c（v3.0）
```

すべてのモジュールは共通ヘッダ `debugger.h`（`debugger_t`, `breakpoint_t`, `thread_entry_t`（v2.0）, `process_entry_t`（v3.0）定義、`<windows.h>`, `<dbghelp.h>` インクルード）に依存する。

`cmdline_parser.y`/`cmdline_lexer.l` と `expr_parser.y`/`expr_lexer.l` は、それぞれ `win_bison -d`/`win_flex` で
`*.tab.c`/`*.tab.h`（bison）・`*.yy.c`/対応する `.h`（flex）を生成し、生成物を `commands.c`/`expr.c` と共に
コンパイルする（`make.bat`／`tdb.vcxproj` の `CustomBuild` ステップ参照）。両文法はそれぞれ独立した
bison `%define api.prefix`（`eparse`/`cparse`）と flex `%option prefix` を用いて生成シンボル名を分離しており、
同一実行ファイル内でリンクしても `yylex`/`yyparse` 等の名前が衝突しない。

## 3. 全体処理シーケンス

1. `main()`（main.c）: 引数チェック（`argc == 2`）→ `debugger_start()` → 成功時 `debugger_loop()` を呼び出す。
2. `debugger_start()`（debugger.c）: `CreateProcessA(..., DEBUG_ONLY_THIS_PROCESS, ...)` でデバッギを生成し、`debugger_t` にハンドル・PID/TID・対象パスを設定、`print_pretty=1` を初期化。
3. `debugger_loop()`（debugger.c）: `WaitForDebugEvent` → イベント種別ごとの処理 → `ContinueDebugEvent` のループ。ブレークポイント／例外／プロセス終了時には `command_loop()` を呼び出し、ユーザー入力待ちに入る。
4. `command_loop()`（commands.c）: `fgets` で 1 行読み取り→`cmd_dispatch()`（`cmdline_parser.y`、v1.9）にその行を渡す→bison/flex 文法でキーワード・引数を認識し対応する `do_xxx()` ハンドラを呼び出す。`do_si`/`do_continue`/`do_step`/`do_next`/`do_up`/`do_run`/`do_kill` は `cmd_action_t* action` に `CMD_RETURN` を設定し、`command_loop` はこれを見て関数を `return` してデバッグイベントループへ制御を戻す。それ以外のコマンドは処理後ループを継続する（`CMD_STAY`）。

## 4. 起動・再起動処理設計

### 4.1 `debugger_start`（debugger.c:10-48）

1. `STARTUPINFOA`/`PROCESS_INFORMATION` をゼロ初期化。
2. `CreateProcessA(program, NULL, NULL, NULL, FALSE, DEBUG_PROCESS, NULL, NULL, &si, &pi)` を実行。
   - **v3.0 での変更**: 従来は `DEBUG_ONLY_THIS_PROCESS`（ルートプロセスのみをデバッグ対象とし、それが生成する子プロセスは一切通知されない）を指定していたが、`DEBUG_PROCESS`（ルートプロセスとその子孫プロセス全体を同じ `WaitForDebugEvent` ループでデバッグ対象にする）へ変更した。これにより、対象プログラム（またはその子孫）が生成する子プロセスのイベントも同じイベントループへ届くようになる（18 章参照）。
3. 失敗時は `GetLastError()` を表示し `-1` を返す。
4. 成功時、`dbg->process/thread/pid/tid` を設定し、`print_pretty=1`、`sym_handle = dbg->process`（実際のデバッギプロセスハンドル。v1.4 で `GetCurrentProcess()` から変更。10.4 節参照）を設定。`dbg->image_path` にも同じ対象パスを設定する（v3.0、ルートプロセス自身の実行ファイルパスとして。2.1 節参照）。
5. `target_program` に対象パスを保存（`run` での再起動用）。
6. この時点ではメインスレッドはまだ `dbg->threads`（スレッドレジストリ、17 章参照）へ登録されていない。登録は `debugger_loop` の `CREATE_PROCESS_DEBUG_EVENT` 処理（5.1 節）で行う（v2.0）。

### 4.2 `debugger_restart`（debugger.c:50-77）

1. `target_program` を一時変数へ退避。
2. `breakpoints` 連結リストを全解放。
3. `free_all_threads(dbg)`（threads.c、17.1 節）でスレッドレジストリのノードを全解放する（v2.0）。ハンドルは `CloseHandle` しない — 対象プロセス自体が終了済み（もしくはこれから `kill`/再起動で終了する）前提のため、既存の `dbg->process`/`dbg->thread` を再起動時に明示的にクローズしない従来の方針に合わせている。
3.1. `free_all_processes(dbg)`（processes.c、18.1 節）で、非アクティブプロセスの状態退避リスト（`dbg->processes`）のノードも同様に全解放する（v3.0）。
4. `sym_handle` が有効なら `SymCleanup`。
5. `debugger_t` 全体を `memset` でゼロクリアし、退避しておいたパスを再設定。
6. `debugger_start()` を呼び直し、`debugger_loop()` を再度開始する（`run` コマンドから呼ばれた場合、呼び出し元の `command_loop` へは戻らない設計）。

## 5. デバッグイベントループ設計（`debugger_loop`, debugger.c:79-318）

`WaitForDebugEvent` で取得した `DEBUG_EVENT.dwDebugEventCode` により分岐する。

### 5.1 `CREATE_PROCESS_DEBUG_EVENT`

`ev.dwProcessId == dbg->pid`（ルートプロセス自身の、最初の 1 回だけ発生するイベント）か否かで分岐する（v3.0）。

**ルートプロセスの場合**（従来通り）:

1. `dbg->tid = ev.dwThreadId` を設定（メインスレッドの TID。`debugger_start` で設定済みの値と同じ）。
2. `register_thread(dbg, dbg->tid, dbg->thread)`（threads.c、17.1 節、v2.0）でメインスレッドをスレッドレジストリへ登録する。`dbg->thread` は `debugger_start` の時点ですでにメインスレッドの正しいハンドル（`CreateProcessA` が返した `pi.hThread`）を保持しているため、ここでは追加のハンドル取得は不要。
3. ベースアドレスを表示。
4. `init_symbols(dbg)` で `SymInitialize` を実行。
5. `SymLoadModuleEx(dbg->sym_handle, NULL, dbg->target_program, NULL, (DWORD64)lpBaseOfImage, 0, NULL, 0)` でモジュールをロードする。
   - **v1.3 での修正**: 従来はモジュール名が `"testprog.exe"` に固定されており、それ以外のファイル名の対象を渡すと（実際にはたまたま同名の `testprog.exe` が同一ディレクトリに存在する場合を除き）誤ったモジュール名でロードされ、シンボル・ソース行が一切解決できなくなる不具合があった。`testprog2.c`（1.1 節参照）を新たなデバッグ対象として追加検証した際にこの不具合が顕在化したため、実際に起動した対象パスを保持する `dbg->target_program` を渡すよう修正した。

**子プロセスの場合**（新設、v3.0、18.2 節参照）:

1. `QueryFullProcessImageNameA(ev.u.CreateProcessInfo.hProcess, 0, path, &size)` でこの子プロセスの実行ファイルパスを取得する。
2. `register_new_process(dbg, ev.dwProcessId, ev.u.CreateProcessInfo.hProcess)`（processes.c、18.1 節）で新規の `process_entry_t` をバックグラウンドリスト（`dbg->processes`）へ追加する。この時点ではフォーカスを奪わない（スレッド生成時と同じ方針、5.1.1 節参照）。
3. 一時的に `switch_active_process(dbg, ev.dwProcessId)` でこの子プロセスをアクティブへ切り替え、`dbg->sym_handle = dbg->process` を設定したうえで `register_thread`・`init_symbols`・`SymLoadModuleEx` をこの子プロセス自身に対して行う（＝子プロセスは自分自身の実行ファイルに対応するシンボルを、自分自身のシンボルハンドルで独立して解決する）。
4. `switch_active_process(dbg, prev_pid)` で元のアクティブプロセスへ戻す。
5. `process created id=<PID>` を表示する。`command_loop` は呼ばず、対話プロンプトを止めずに自動的に実行を継続する。

### 5.1.1 `CREATE_THREAD_DEBUG_EVENT`（新設、v2.0）

対象プログラムが新しいスレッドを生成すると発生する。イベントの発生元プロセス（`ev.dwProcessId`）がアクティブなプロセスかどうかで、登録先のスレッドレジストリを切り替える（v3.0）: アクティブなプロセス（`dbg->pid`）であれば `&dbg->threads`、そうでなければ `find_background_process(dbg, ev.dwProcessId)` で見つけた `process_entry_t` の `&entry->threads` を対象にする。これにより、フォーカスしていない別プロセスのスレッド生成イベントでも、アクティブプロセスの `dbg->threads` を誤って書き換えることがない。

1. 上記のとおり登録先リストを決定し、`register_thread(&list, ev.dwThreadId, ev.u.CreateThread.hThread)`（threads.c）でスレッドレジストリへ追加する。
2. ウォッチポイントの再適用も同様に分岐する（v3.0）: イベントがアクティブなプロセスのものであれば従来通り `apply_watchpoints(dbg)`（watchpoints.c、7.5.1 節）を呼び直す。バックグラウンドの別プロセスのものであれば、汎用化した `apply_watchpoints_to_thread(entry->watchpoints, entry->watch_count, handle)`（watchpoints.c）を呼び、そのプロセス自身が退避保持しているウォッチポイント設定を新しいスレッドの DR0〜DR3/DR7 に適用する。
3. `thread created id=<TID>` を表示する。
4. **`dbg->tid`/`dbg->thread` は変更しない** — 進行中の `step`/`next`/ブレークポイント再武装シーケンスなど「現在フォーカス中のスレッド」に関する状態を乱さないようにするため、意図的にこのイベントでは触れない。
5. `command_loop` は呼ばず、対話プロンプトを止めずに自動的に実行を継続する。

### 5.1.2 `EXIT_THREAD_DEBUG_EVENT`（新設、v2.0）

対象プログラムのいずれかのスレッドが終了すると発生する。

1. `thread exited id=<TID> exit code=<code>` を表示する。
2. `dbg->locked_tid == ev.dwThreadId`（すなわちフォーカス固定先が今まさに終了するスレッドである）場合、`dbg->locked_tid = 0` としてフォーカス固定を解除する。固定したままにすると、以後どのスレッドも「フォーカス外」と判定され続け、実質的に二度と対話プロンプトへ戻れなくなってしまうため（5.2 節参照）。
3. `CREATE_THREAD_DEBUG_EVENT` と同様、削除先のスレッドレジストリはイベントの発生元プロセスがアクティブかどうかで分岐する（v3.0）。決定したリストに対して `unregister_thread(&list, ev.dwThreadId)`（threads.c）でスレッドレジストリから削除し、ハンドルを `CloseHandle` する。
4. `dbg->tid`/`dbg->thread` は変更せず、`command_loop` も呼ばない。

### 5.2 `EXCEPTION_DEBUG_EVENT`

先頭で以下を行う（v2.0、v3.0）:

```c
if (ev.dwProcessId != dbg->pid)
    switch_active_process(dbg, ev.dwProcessId);

dbg->tid = ev.dwThreadId;
dbg->thread = find_thread_handle(dbg, dbg->tid);
int auto_continue = (dbg->locked_tid != 0 && dbg->tid != dbg->locked_tid);
```

**`switch_active_process` 呼び出し（v3.0 で追加）**: このイベントの発生元プロセスが現在アクティブなプロセスと異なる場合、以降の処理より前にアクティブプロセスを切り替える。これにより、以降のブレークポイント判定（`find_breakpoint`）・ウォッチポイント判定（`watchpoint_hit_slot`）・シンボル解決・フォーカス自動固定判定などが、すべて「切替後の（イベントを実際に発生させた）プロセス」の状態を対象に動作する。既存のスレッド向けロジックを一切変更せずにプロセスをまたいで正しく動作させられるのは、この 1 行の切替のおかげである（18 章参照）。

`dbg->tid`/`dbg->thread` を毎回このイベントの発生元スレッドへ正しく解決する（**v2.0 での修正**: 従来は `dbg->tid` のみがイベントごとに上書きされ `dbg->thread` は起動時のメインスレッドのハンドルに固定されたままだったため、2 本目以降のスレッドが発生させたイベントは誤ったスレッドのハンドルに対して `GetThreadContext`/`SetThreadContext` 等を行ってしまう不具合があった）。

`auto_continue` は「フォーカス固定中（`locked_tid != 0`）かつ、このイベントの発生元スレッドがフォーカス先と異なる」ことを表す。下記 3.・4. のうちトラッキング済みブレークポイント・ウォッチポイント・ステップ着地の各分岐は、`auto_continue` が真の場合、詳細表示（PID/TID・ソース行・逆アセンブル）と `command_loop` 呼び出しを省略し、1 行の簡潔な通知（例: `thread id=1234 hit breakpoint at 0x... (not focused, continuing)`）のみを表示して自動的に実行を継続する。逆に `auto_continue` が偽で実際に表示する場合は、その時点で `dbg->locked_tid = dbg->tid` を設定し、そのスレッドへフォーカスを（再）固定する。未トラッキングのブレークポイント（下記 3. の「見つからない場合」）や Ctrl+C 割り込みはこの判定に関わらず常に表示・停止し、フォーカス固定のトリガーにもしない（詳細は 17.3 節）。

例外コードにより次のように分岐する。

0. **Ctrl+C 割り込み**（`DBG_CONTROL_C` = 0x40010005）
   - `GetThreadContext` で現在の RIP を取得し、割り込みメッセージを表示。
   - PID/TID（`dbg->pid`/`dbg->tid`）を表示したうえで、ソース行または逆アセンブル 1 行を表示して `command_loop()` に戻る。

1. **アクセス違反**（`EXCEPTION_ACCESS_VIOLATION` = 0xc0000005）
   - システム CRT 内で発生したアクセス違反は無視して実行を継続する。
   - 例外情報を表示後、`command_loop()` に入らずに `break` して実行を再開。

2. **一時ブレークポイントヒット**（`EXCEPTION_BREAKPOINT` かつ `dbg->temp_bp_addr != NULL`）
   - `remove_temp_breakpoint()` で元バイトへ復元。
   - `CONTEXT.Rip` を `-1`（INT3 の直後から命令先頭へ）補正して書き戻す。
   - `next_mode` が有効な場合、現在行が `next_line` と一致するなら `single_step()` を実行して即座に `break` で抜け、次のイベント待ちへ戻る（ステップオーバー中の継続判定）。行が変わっていれば `next_mode` を解除。
   - それ以外は、`auto_continue` が真なら 1 行の簡潔な通知（`thread id=<TID> returned to 0x... (not focused, continuing)`）のみを表示する。偽なら `dbg->locked_tid = dbg->tid` でフォーカスを（再）固定したうえで復帰先アドレスを表示し `show_source_line()` を呼ぶ（v2.0）。
3. **恒久ブレークポイントヒット**（`EXCEPTION_BREAKPOINT` かつ上記以外）
   - `ctx.Rip - 1` を実際のヒットアドレスとして `find_breakpoint()` で検索。
   - 見つかった場合 `remove_breakpoint_at()` で元バイトへ復元し、`Rip` を補正した**後**に `arm_breakpoint_rearm()`（7.4 節、v1.5 で追加）を呼んで次回ヒットに備え、続けて `suspend_other_threads()`（17.2 節、v2.0）で他スレッドを一時停止する。`auto_continue` が真なら 1 行の簡潔な通知（`thread id=<TID> hit breakpoint at <addr> (not focused, continuing)`）のみを表示し、偽なら `dbg->locked_tid = dbg->tid` でフォーカスを（再）固定したうえで PID/TID を表示してソース行 or （行情報が無ければ）逆アセンブル 1 行を表示。
   - 見つからない場合（トラップフラグ由来の INT3 等）は「追跡していないブレークポイント」として素通しでメッセージと PID/TID を表示する。`auto_continue`/フォーカス固定の判定は行わず常に表示する（起動直後の ntdll 初期停止がこの分岐に該当するため、フォーカス固定のトリガーにしないという方針、5.2 節参照）（v2.0）。
4. **シングルステップ例外**（例外コード `0x80000004` = `STATUS_SINGLE_STEP`）
   - 先頭でハードウェアウォッチポイントのヒット判定（`watch_count > 0` かつ `watchpoint_hit_slot()` が 0 以上）を行う。ヒットしていれば `watchpoint_report()`＋PID/TID を表示し、`auto_continue` が真なら `(not focused, continuing)` の 1 行のみで `break`、偽なら `dbg->locked_tid = dbg->tid` でフォーカスを（再）固定したうえでソース行を表示して `command_loop()` に入る（v2.0、7.5.1 節参照）。
   - `breakpoint_rearm_pending(dbg)`（7.4 節）を確認し、保留中なら `finish_breakpoint_rearm()` で `0xCC` を書き戻した後 `resume_other_threads()`（17.2 節、v2.0）で恒久ブレークポイントヒット時に一時停止した他スレッドを再開する。`next_mode`/`step_mode` が有効ならさらに `single_step()` を呼んで `break`（内部消費）。`dbg->si_requested` が立っていれば握りつぶさずそのまま下記の表示処理へフォールスルーする。
   - `next_mode` が有効な場合: 現在行が不明（`cur_line==0`、関数呼び出し中など）ならスタック上のリターンアドレスを読み取り `set_temp_breakpoint()` を設定して実行再開（＝呼び出し先をスキップ）。行が `next_line` と一致すればさらに `single_step()` して継続、不一致なら `next_mode` 解除。
   - `step_mode` が有効な場合: 行が不明または `step_line` と一致する間は `single_step()` を継続、行が変わったら `step_mode` 解除。
   - いずれの継続条件にも当てはまらない場合、`auto_continue` が真ならここで `break`（無表示）、偽なら `dbg->locked_tid = dbg->tid` でフォーカスを（再）固定したうえで現在の RIP と PID/TID、ソース行を表示する（v2.0）。
5. 上記いずれの分岐でもソース行が未表示（`source_shown==0`）であれば、最後に現在の例外コード・RIP・PID/TID を表示したうえでソース行表示を試みる。**`auto_continue` が真の場合はこの共通表示自体を丸ごとスキップし、`list_next_line`/`list_file` のリセットのみ行って `break` する（v2.0）**。
6. `list_next_line`/`list_file` をリセットしたうえで `command_loop(dbg)` を呼び出し、ユーザー入力を待つ。

### 5.3 `EXIT_PROCESS_DEBUG_EVENT`

`unregister_process(dbg, ev.dwProcessId, ev.u.ExitProcess.dwExitCode)`（processes.c、18.1 節、v3.0）を呼ぶ。この関数が内部で行う処理は次の通り。

1. `process exited id=<PID> exit code=<code>` を表示する。終了したプロセスで `leak_tracking` が有効だった場合は `print_leaks`（16 章参照）でリーク一覧も表示する。
2. 終了したのが**非アクティブな**プロセスであれば、いったん `switch_active_process()` でそのプロセスをアクティブへ切り替えてから、次の「アクティブプロセス終了」処理を行う。
3. **アクティブプロセス終了処理**: ブレークポイント・確保情報・スレッド一覧などそのプロセス固有のリソースを解放する。終了したプロセスの中のいずれかのスレッドに `locked_tid` が向いていた場合は解除する。
4. `dbg->processes`（バックグラウンドリスト）に他のプロセスがまだ残っていれば、その先頭を新しいアクティブプロセスへ昇格させ、戻り値として「まだ他プロセスが残っている」ことを返す。1 つも残っていなければ「もう残っていない」ことを返す。

呼び出し元（`debugger_loop`）は戻り値により分岐する（v3.0）:
- 戻り値が「残っていない」場合: 従来通り `ContinueDebugEvent` を呼んだ後 `command_loop(dbg)` を呼び出し（`quit` 入力を待つ状態）、`return` でループを終了する。
- 戻り値が「まだ残っている」場合: `command_loop` は呼ばず、`break` して `debugger_loop` のイベント待ちを継続する（子プロセスの終了、あるいはルートプロセスの終了後も他プロセスが残っている場合はこちら）。

### 5.3.1 malloc/free サイレント計装（`leak_tracking`）

`EXCEPTION_DEBUG_EVENT` の `int source_shown = 0;` 直後、既存の `temp_bp_addr`/ユーザーブレークポイント判定より前に、`leak_tracking` 有効時のみ働く分岐を追加している。ヒットアドレスが `malloc_addr`/`free_addr`/`malloc_ret_addr` のいずれかであれば、（確保関数のリターン捕捉である `malloc_ret_addr` 以外は）`suspend_other_threads()`（17.2 節、v2.0）で他スレッドを一時停止したうえで、対応する `leak_on_malloc_enter`/`leak_on_free_enter`/`leak_on_malloc_return`（16 章参照）を呼んだ後 `command_loop` を呼ばずに `break` して switch を抜ける。ループ末尾の既存の `ContinueDebugEvent` がそのまま実行されるため、ユーザーから見て対話プロンプトが一切止まらない「サイレント」な計装になる。

同様に `STATUS_SINGLE_STEP`（`0x80000004`）の処理先頭でも `leak_rearm_addr` が保留中かを確認し、保留中であれば `leak_finish_rearm()` で `0xCC` を書き戻してから `resume_other_threads()`（17.2 節、v2.0）で一時停止した他スレッドを再開し、`next_mode`/`step_mode` が同時に有効な場合のみ `single_step()` を呼び直して `break` する（詳細は 16 章）。

**マルチスレッド対応（v2.0）に関する制約**: 上記の他スレッド一時停止はエントリフック（`malloc`/`calloc`/`realloc`/`free` それぞれのエントリアドレスの再武装区間）のみを保護する。確保関数のリターンアドレス追跡用の一時ブレークポイント（`malloc_ret_addr`）は単一スロットのため、複数スレッドが同時に確保関数の内部を実行中の場合はこの部分の追跡が競合しうる（未解決の既知の制約。要件定義書 8 章参照）。

### 5.4 ステップ実行の状態遷移（`next_mode` / `step_mode`）

```
[停止中] --si/step/n入力--> single_step() で TF フラグセット --> 実行再開
   └─ STATUS_SINGLE_STEP 発生
        ├─ next_mode: 行不明→呼び出し先に一時BP設置して抜ける
        │             行一致→再度single_step（同一行内をスキップ）
        │             行不一致→next_mode解除・停止・表示
        └─ step_mode: 行不明 or 行一致→再度single_step
                      行不一致→step_mode解除・停止・表示
```

## 6. コマンド処理設計（`command_loop`, commands.c / `cmdline_parser.y` / `cmdline_lexer.l`）

**v1.9 で全面改訂**: 従来は `command_loop` 自体が `strncmp`/文字比較による前方一致の `if/else if` チェーンでコマンド判定を行っていた（判定順序に依存し、`p` で始まる文字列を無条件に `print` として扱う、`x` で始まる文字列を無条件に `x` として扱う等、過度に緩い判定が残っていた）。v1.9 でこの判定部分を bison/flex 生成の文法（`cmdline_parser.y`/`cmdline_lexer.l`）へ置き換え、`command_loop` は 1 行読み取り（`fgets`）と `cmd_dispatch()` 呼び出しのみを担当する薄いループになった。各コマンドの実処理（アドレス解決・フラグ解析等）自体は従来通り `commands.c` の関数（`do_xxx()` という命名に統一）が担う。

### 6.1 全体構成

```
command_loop(dbg)                         … commands.c（読み取りループのみ）
  └─ cmd_dispatch(dbg, line, &action)      … cmdline_parser.y（文法のエントリポイント）
       ├─ cparse_reset_state()             … cmdline_lexer.l。flex の開始条件をリセット
       ├─ cparse_scan_string(line)         … 1 行分のバッファをセットアップ
       ├─ cparseparse(dbg, &action)        … bison 生成の構文解析。文法アクションが do_xxx() を呼ぶ
       └─ cparse_delete_buffer()
```

`cmd_action_t action`（`cmdline_internal.h`）は `CMD_STAY`（既定値。ループ継続）と `CMD_RETURN`（`command_loop` から `return` してデバッグイベントループへ戻る）の 2 値。`do_si`/`do_continue`/`do_step`/`do_next`/`do_up`/`do_run`/`do_kill` が `*action = CMD_RETURN` を設定する（`do_run`/`do_kill` は内部条件により設定有無が分かれる。6.3 節参照）。`do_quit` 相当の処理は文法アクションから直接 `exit(0)` を呼ぶため `action` を経由しない。

### 6.2 字句解析（`cmdline_lexer.l`）

flex の開始条件（start condition）を 3 つ使用する。

| 状態 | 用途 |
|---|---|
| `INITIAL` | 行頭でのコマンドキーワード認識、および単語引数（`ARGWORD`）の取り込み |
| `RAWLINE` | キーワードの直後、行末までを 1 つの生文字列引数（`STRING`）として取り込む |
| `SKIPREST` | 引数を取り込んだ後、行の残り（想定外の余分な入力）を読み捨てて次のコマンドに備える |

コマンドキーワードはすべて行頭アンカー（`^`）付きで、かつ後続文字が識別子構成文字（英数字・アンダースコア）でないことをトレイリングコンテキスト（`/[^A-Za-z0-9_]`）で要求する単語境界一致になっている。これにより旧実装にあった「`p` で始まる文字列は無条件に `print` 扱い」「`x` で始まる文字列は無条件に `x` 扱い」といった過度に緩い判定は解消され、`break`/`b`、`print`/`p`、`list`/`l`、`step`/`s`、`continue`/`c`、`help`/`h` のような正規のエイリアスのみが対応するキーワードとして認識される。

引数の取り込み方は、旧実装の各コマンドが実際に読んでいた範囲に合わせて 2 種類に分けている。

- **単語引数（`ARGWORD`）**: `break`/`del`/`wdel`/`syms` は最初の空白区切り 1 語のみを引数として取り込み、`BEGIN(SKIPREST)` で残りを読み捨てる（旧実装の `sscanf_s(line, "%*s %127s", ...)` と同じ挙動）。
- **行末までの生文字列（`STRING`）**: `x`/`dis`/`list`/`lines`/`leak`/`show`/`watch`/`print`/`set`/`set print pretty`/`help` は `BEGIN(RAWLINE)` で行末までを 1 トークンとして取り込む（前後の空白は取り込み時にトリムする）。引数が全く無い場合（例: `dis\n`）も空文字列の `STRING` として必ず生成される。

**実装上の注意点（開発時に発見した具体的な不具合とその対処）**:

1. **フラグがキーワードへ直接連結する構文の誤認識**: `print`/`watch` はそれぞれ `p/x`（空白無しで `/fmt` が直後に続く）、`watch/r`（空白無しで `/r` が直後に続く）という記法を許容する（旧実装の `arg` 解析がそうなっていたため）。単純に `"print"/{境界}` という規則だけを書くと、flex の最長一致規則により `[^ \t\r\n]+`（`ARGWORD`/フォールバック用の規則）が `"print/x"` 全体（7 文字）にマッチしてしまい、`"print"`（5 文字）だけにマッチするキーワード規則より優先されてしまう。これを避けるため、`"print""/"[^ \t\r\n]*` のようにフラグ部分も一旦まとめて貪欲にマッチさせたうえで `yyless(5)` により `"print"` の 5 文字だけを消費済み扱いにし、残り（`/x ...`）を `RAWLINE` 側で再度読み取らせるようにした。
2. **行頭アンカーの付け忘れ**: 実装初期のバージョンでは各キーワード規則に `^` を付け忘れており、例えば `wdel x` の引数 `x` が（`x` コマンドのキーワード規則が行頭以外でもマッチしてしまうため）別のコマンドトークンとして誤認識され、構文エラーで `wdel` 自体の処理が行われない不具合があった。全キーワード規則に `^` を付与して解消した。
3. **`cmd_dispatch` 呼び出し間での flex 開始条件の持ち越し**: `cparse_scan_string()` はバッファを切り替えるだけで、flex の開始条件（`yy_start` 相当の内部状態）はリセットされない。直前の行が構文エラー等で `RAWLINE`/`SKIPREST` 状態のまま処理を終えていた場合、次の `cmd_dispatch()` 呼び出しがその状態を引き継いでしまい、以降のコマンドが軒並み誤動作する不具合があった。`cmd_dispatch()` の先頭で明示的に `cparse_reset_state()`（`cmdline_lexer.l` 内で `BEGIN(INITIAL)` するだけの小さな公開関数）を呼ぶことで解消した。
4. **空文字列引数のトークンが生成されない**: `RAWLINE` 状態の規則を単純に `[^\r\n]*`（0 文字以上）とすると、引数が全く無い場合（例: `dis\n` の `dis` の直後）にマッチ長が 0 となり、flex がこの規則を発火させず `STRING` トークンが一切生成されない（結果として `dis`/`list`/`show`/`watch` 等を引数無しで実行すると何も起きない）という問題があった。`cmd_dispatch()` が渡す行には必ず末尾に改行を保証しているため、規則を `[^\n]*\n?`（末尾の改行を含めてマッチさせる）に変更し、マッチ長を常に 1 文字以上に保証することで解消した。

### 6.3 構文解析（`cmdline_parser.y`）とコマンド対応表

文法は「キーワード（＋任意のフラグ）＋ `ARGWORD` または `STRING`」という単純な形をコマンドの数だけ列挙したものであり、判定順序に意味は無い（曖昧性はキーワードと `ARGWORD`/`STRING` の間で lookahead 1 トークンにより一意に解決される）。

| コマンド | 文法上の形 | 呼出先（`commands.c`） | 備考 |
|---|---|---|---|
| `break` / `b` | `KW_BREAK ARGWORD` \| `KW_BREAK` | `do_break` | 引数解決は `resolve_addr_spec(dbg, arg, 1)`（プロローグスキップあり）で `del` と共通化 |
| `del` | `KW_DEL ARGWORD` \| `KW_DEL` | `do_del` | 引数がすべて数字（先頭の `#` は許容）なら `find_breakpoint_by_index()` で `show bp` の表示番号として解決し（v1.10）、そうでなければ `resolve_addr_spec` に委譲 |
| `wdel` | `KW_WDEL ARGWORD` \| `KW_WDEL` | `do_wdel` | `0x` 直値／シンボル名のみ（`resolve_addr_spec` は使わない） |
| `syms` | `KW_SYMS ARGWORD` \| `KW_SYMS` | `do_syms` | `print_symbol_info()` を呼ぶ |
| `regs` | `KW_REGS` | `do_regs` | `show_registers()` |
| `si` | `KW_SI` | `do_si` | `*action = CMD_RETURN` |
| `continue` / `c` | `KW_CONTINUE` | `do_continue` | `*action = CMD_RETURN` |
| `step` / `s` | `KW_STEP` | `do_step` | 行情報が無ければ `si` にフォールバック。`*action = CMD_RETURN` |
| `n` | `KW_N` | `do_next` | 同上 |
| `up` | `KW_UP` | `do_up` | `*action = CMD_RETURN` |
| `run` | `KW_RUN` | `do_run` | 対象パスが有る場合のみ `*action = CMD_RETURN` |
| `kill` | `KW_KILL` | `do_kill` | 常に `*action = CMD_RETURN` |
| `tb` | `KW_TB` | `do_tb` | `print_backtrace()` |
| `help` / `h` | `KW_HELP STRING` | `do_help` | 引数（コマンド名／エイリアス）指定時は詳細説明を表示。v1.9 で追加（6.4 節） |
| `quit` | `KW_QUIT` | 文法アクションから直接 `exit(0)` | — |
| `x` | `KW_X STRING` | `do_x` | `rsp±N`/`rbp±N`/直値アドレスを解決 |
| `dis` | `KW_DIS STRING` | `do_dis` | 引数無しは現在 RIP から |
| `list` / `l` | `KW_LIST STRING` | `do_list` | 継続表示状態は `dbg->list_file`/`list_next_line` |
| `lines` | `KW_LINES STRING` | `do_lines` | `print_line_info()` |
| `leak` | `KW_LEAK STRING` | `do_leak` | `on`/`off` |
| `show` | `KW_SHOW STRING` | `do_show` | `bp`/`leaks`/`wp`/`threads`（v2.0）/`processes`（v3.0）は専用表示、それ以外は `show_variables()` |
| `thread` | `KW_THREAD ARGWORD` \| `KW_THREAD` | `do_thread` | `lock`/`unlock`、または TID 直値でフォーカス切替（v2.0、17.3 節） |
| `process` | `KW_PROCESS ARGWORD` \| `KW_PROCESS` | `do_process` | PID 直値でアクティブプロセス切替（v3.0、18.2 節） |
| `watch` | `KW_WATCH STRING` | `do_watch` | フラグ解析は文字列内で従来通り実施 |
| `set print pretty` | `KW_SETPRINTPRETTY STRING` | `do_set_print_pretty` | `set` の他の形より先に判定される（文法上、字句解析側で `"set print pretty"` の方が長くマッチするため） |
| `set` | `KW_SET STRING` | `do_set` | `lhs = rhs` の分解は従来通り文字列処理で実施 |
| （未認識のコマンド） | `ARGWORD` | `do_unknown` | 「unknown command」を表示 |
| （空行） | `%empty` | なし | 何も表示しない |

`resolve_addr_spec(dbg, arg, skip_prologue)`（`commands.c`、v1.9 で新設）は、旧実装で `break`/`del` の 2 箇所に一字一句同じ内容で重複していた「`:` を含めば file:line、`0x` 始まりなら直値アドレス、それ以外はシンボル名解決（`skip_prologue` が真なら `skip_function_prologue()` を追加適用）」というアドレス解決ロジックを共通関数へ切り出したものである。

### 6.4 `help` コマンドの詳細説明（v1.9 で追加）

`do_help(arg)` はコマンド名（引数）を静的テーブル `help_table[]`（`commands.c`）から大小文字を区別せず（`_stricmp`）検索する。

- 引数省略時: 従来通りのコマンド一覧（`print_help_summary()`）を表示する。
- 引数が `help_table[]` のいずれかのエントリ（コマンド名またはそのエイリアス、例: `p`→`print`、`s`→`step`）に一致する場合: そのコマンドの用法（`usage:` 行）とオプション・引数の意味・使用例を含む複数行の詳細説明を表示する。
- 一致しない場合: 「no help available for '...'」に続けて、有効なトピック名（`help_table[]` の各エントリの主名）一覧を表示する。

字句解析側では `help`/`h` を（従来の「引数無しのみ許可」グループから）`x`/`dis` 等と同じ「行末までの生文字列を取り込む」グループへ変更しており、`h`（1 文字エイリアス）についても `help` と同様に引数を続けて指定できる（例: `h si`）。

## 7. ウォッチポイント管理設計（watchpoints.c）

### 7.1 ハードウェアデバッグレジスタ構成

x86/x64 には 4 個のデバッグアドレスレジスタ（DR0〜DR3）と制御レジスタ DR7、ステータスレジスタ DR6 がある。

| DR6 ビット | 意味 |
|---|---|
| 0−3 | DR0〜DR3 のいずれかがヒット |

| DR7 ビット | 意味 |
|---|---|
| 0,2,4,6 | DR0〜DR3 のローカル有効ビット |
| 16-17,20-21,24-25,28-29 | 条件（00=実行, 01=書き込み, 11=読み書き）（スロットごと） |
| 18-19,22-23,26-27,30-31 | サイズ（00=1B, 01=2B, 10=8B, 11=4B）（スロットごと） |

### 7.2 `set_watchpoint`（watchpoints.c）

1. スロット数・重複・サイズチェック。
2. `watchpoints[watch_count]` にアドレス・タイプ・サイズ・スロットを記録。
3. `apply_watchpoints()` で `GetThreadContext`（`CONTEXT_DEBUG_REGISTERS`）→ DR0〜DR3 ・ DR7 を再構成 → `SetThreadContext`。

### 7.3 `remove_watchpoint`（watchpoints.c）

配列を縮小して `watch_count--`。`apply_watchpoints()` でレジスタを再設定。

### 7.4 `watchpoint_hit_slot`（watchpoints.c）

`GetThreadContext`（`CONTEXT_DEBUG_REGISTERS`）で DR6 を読み、ビット 0−3 をスキャン。ヒットしたスロットのビットをクリアしてスロット番号を返す。ヒットなしなら -1。

### 7.5 ウォッチポイントヒットの検出（debugger.c）

`STATUS_SINGLE_STEP`（0x80000004）例外の先頭で `watch_count > 0` をチェックし、`watchpoint_hit_slot()` を呼ぶ。戻り値 ≥ 0 なら：

1. `watchpoint_report()` でヒット情報を表示。
2. PID/TID を表示。`auto_continue`（5.2 節、v2.0）が真の場合はここで `(not focused, continuing)` のみ表示して `break`。
3. 偽の場合、`dbg->locked_tid = dbg->tid` でフォーカスを（再）固定したうえでソース行（なければ逆アセンブル 1 行）を表示。
4. `command_loop(dbg)` でユーザー入力待ちに入る。
5. ウォッチポイントが関与しない通常のシングルステップ（bp rearm/step/next/si）は従来どおり後続の処理へ流れる。

### 7.5.1 全スレッド適用（v2.0）

DR0〜DR3/DR7 はスレッドごとの CPU レジスタであるため、v2.0 以前は `apply_watchpoints()`（7.2 節の `set_watchpoint`/7.3 節の `remove_watchpoint` から呼ばれる内部関数）が `dbg->thread`（当時は起動時のメインスレッドのハンドルに固定）にしか設定を適用しておらず、他スレッドが監視対象アドレスへ書き込み／読み取りを行ってもウォッチポイントは検知できなかった。`apply_watchpoints()` を、`dbg->threads`（スレッドレジストリ、17 章）を走査して登録済みの全スレッドへ同じ DR0〜DR3/DR7 設定を適用する実装に変更し解消した。また、`CREATE_THREAD_DEBUG_EVENT`（5.1.1 節）でも新規スレッドの登録直後に `apply_watchpoints()` を呼び直すことで、ウォッチポイント設定後に生成されたスレッドにも既存の監視設定が及ぶようにしている。`watchpoint_hit_slot()`（7.4 節）自体は変更不要 — `dbg->thread` は 5.2 節の修正により当該イベントの発生元スレッドへ正しく解決されているため、実際に DR6 ステータスビットを立てたスレッドの情報をそのまま読み取れる。

## 8. ブレークポイント管理設計（breakpoints.c）

### 7.1 恒久ブレークポイント

- `find_breakpoint(dbg, addr)`: 連結リストを線形探索しアドレス一致要素を返す。
- `find_breakpoint_by_index(dbg, index)`（v1.10 で新設）: `print_breakpoints`（7.3 節）が表示する 1 始まりの表示インデックス（`show bp` の `#N`）と同じ順序でリストを走査し、`index` 番目の要素を返す。`del` コマンドが `#N`/`N` 形式の引数を解決するために使う（6.3 節参照）。
- `set_breakpoint(dbg, addr)`:
  1. 重複チェック（既存なら何もせずメッセージ表示）。
  2. `breakpoint_t` を `malloc`。
  3. `ReadProcessMemory` で元バイトを 1 バイト読み取り保存。
  4. `WriteProcessMemory` で `0xCC`（INT3）を書き込み。
  5. `FlushInstructionCache` で命令キャッシュを無効化。
  6. リスト先頭へ挿入。
- `remove_breakpoint_at(dbg, addr)`: 該当ブレークポイントを `dbg->breakpoints` 連結リストから取り外して `free()` し（恒久的な削除）、元バイトを書き戻して命令キャッシュをフラッシュする。`del` コマンド（`commands.c` の `do_del`）専用の関数であり、以後 `find_breakpoint`/`find_breakpoint_by_index`/`show bp` からは見えなくなる。
- `restore_breakpoint_byte(dbg, addr, orig_byte)`（v1.10 で新設）: 連結リストには一切触れず、`addr` の元バイトを書き戻して命令キャッシュをフラッシュするだけの関数。ブレークポイントヒット時に一時的に元バイトへ戻す（7.4 節の再武装の準備）用途専用で、`breakpoint_t` ノードは `dbg->breakpoints` に残ったままになる。詳細は 7.4 節の不具合修正（v1.10）を参照。
- `remove_breakpoint(dbg)`: 未実装（何もせず `0` を返すのみ）。呼び出し元も無い。

### 7.2 一時ブレークポイント（`up`/`n` 用）

- `set_temp_breakpoint`/`remove_temp_breakpoint`: `dbg->temp_bp_addr`/`temp_bp_byte` の単一スロットのみを使用するため、同時に有効化できる一時ブレークポイントは 1 つに限られる。この一時ブレークポイントは 7.4 節の再武装対象ではなく、意図的に一回限りで消費される（`up`/`n` はリターン先へ 1 度だけ抜けられればよいため）。

### 7.3 ブレークポイント一覧表示（`print_breakpoints`, `show bp` コマンド用）

- `dbg->breakpoints` 連結リストが空の場合は「no breakpoints set」を表示して終了する。
- リストの各要素について、以下の情報をシンボル解決して 1 行にまとめて表示する（`print_backtrace`（symbols.c, 10.4 節）と同様の手法）。
  1. `SymFromAddr(dbg->sym_handle, addr, &disp, sym)` で関数名とオフセットを解決し、`関数名+0xオフセット` の形式に整形する（解決できない場合は `???`）。
  2. `SymGetLineFromAddr64(dbg->sym_handle, addr, &line_disp, &line)` でソースファイル名・行番号を解決し、`at ファイル名:行番号` を付加する（解決できない場合は付加しない）。
  3. `#インデックス  0xアドレス  in 関数名+0xオフセット [at ファイル名:行番号]` の形式で出力する（インデックスは 1 始まり、連結リストの並び順＝新しく設定したブレークポイントほど先頭）。
- 出力例:
  ```
  #1  0x7ff7cb47f3a8  in add+0x8 at C:\...\testprog.c:17
  #2  0x7ff7cb47f4d7  in main+0x117 at C:\...\testprog.c:31
  ```
- **v1.10 で追加**: ここで表示される `#N` のインデックスは、そのまま `del #N`（または `del N`）で削除対象の指定に使える（`find_breakpoint_by_index`、上記 7.1 節）。インデックスは表示時にリストを都度走査して振り直す一時的な番号（`breakpoint_t` 側に保持しているわけではない）であるため、他のブレークポイントを追加・削除すると同じ番号が指す対象が変わりうる点に注意（例: `#1` を削除すると、それまで `#2` だったものが新たに `#1` になる）。

### 7.4 ブレークポイントの再武装（`arm_breakpoint_rearm` / `breakpoint_rearm_pending` / `finish_breakpoint_rearm`）

**不具合修正（v1.5）**: 従来、恒久ブレークポイントは `remove_breakpoint_at` で元バイトを復元した後、二度と `0xCC` を書き戻さなかったため、**同一アドレスに複数回到達しても最初の 1 回しか停止しなかった**（再帰関数やループの内部に設定したブレークポイントで顕在化）。malloc/free リーク検出（16.4 節）で導入した「復元→単独ステップ→再武装」方式を、恒久ブレークポイント全般に適用して解消した…はずだった（下記 v1.10 参照）。

**不具合修正（v1.10、v1.5 修正の再発／未完了だった問題）**: v1.5 の修正後も、実際には**再帰関数の 2 回目以降のヒットで停止しない**という同じ症状が残っていた。原因は、`debugger.c` のブレークポイントヒット処理が「復元」の実装として `remove_breakpoint_at`（7.1 節）を呼んでいたことだった。この関数は名前も実装も「恒久的な削除」（`del` コマンド用、`dbg->breakpoints` からノードを取り外して `free()` する）であり、一時的な復元用ではない。そのため 1 回目のヒットの時点でブレークポイントのノードがリストから消えてしまい、`arm_breakpoint_rearm` によってデバッギのメモリ上には `0xCC` が正しく再武装される一方、2 回目のヒットでは `find_breakpoint`（EXCEPTION_BREAKPOINT ハンドラ、5.2 節・下記）が該当ノードを見つけられず「追跡していないブレークポイント」（`not tracked`）分岐に入っていた。この分岐は本来 OS 側が後始末する ntdll 起動時ブレークポイント等を想定したものであり、RIP を巻き戻さず元バイトも復元しないため、`0xCC`（1 バイト）の直後から実行が再開され、残りの命令バイト列がずれて不正命令列を実行し、`EXCEPTION_ACCESS_VIOLATION` が延々と発生し続ける（無限ループ的に大量出力される）という重大な症状につながっていた。設計ドキュメント側は「v1.5 でリストから除去しない意図的な設計にした」と記載していたが、実装はそうなっておらず、ドキュメントと実装が食い違っていた。`dbg->breakpoints` を一切変更せず元バイトの書き戻しのみを行う `restore_breakpoint_byte(dbg, addr, orig_byte)`（7.1 節）を新設し、`debugger.c` 側の呼び出しをこちらに差し替えて解消した。`del` コマンド（`remove_breakpoint_at` を使う）や `show bp`/`find_breakpoint_by_index` の動作に影響はない。`testprog2.c` の再帰関数 `factorial(5)` に対する `break factorial` → `continue` の繰り返しで、5 段すべて（`n = 5, 4, 3, 2, 1`）で正しく停止することを確認した。

- `arm_breakpoint_rearm(dbg, addr, orig_byte)`: ブレークポイントヒット時、`restore_breakpoint_byte`（v1.10 以降。7.1 節参照）で元バイトへ復元し `CONTEXT.Rip` を補正した**直後**に呼ぶ。`CONTEXT.EFlags` に TF（`0x100`）を立て、`dbg->bp_rearm_addr`/`bp_rearm_byte` に記録する。この時点では対象アドレスの実命令はまだ実行されていない（`command_loop` に入りユーザー入力を待っている状態）。
  - **呼び出し順序の注意**: `GetThreadContext`/`SetThreadContext` による `Rip` 補正（`debugger.c`）より後に呼ぶ必要がある。先に呼ぶと、この関数が内部で読み書きする `CONTEXT`（TF を立てた版）が、その後の `Rip` 補正用 `SetThreadContext`（古い `CONTEXT` を使用）によって上書きされ、TF が消えてしまう。
- `breakpoint_rearm_pending(dbg)` / `finish_breakpoint_rearm(dbg)`: `debugger.c` の `STATUS_SINGLE_STEP` 処理の先頭で呼ばれる。`bp_rearm_addr` が非 NULL なら `0xCC` を書き戻して `bp_rearm_addr` をクリアする。

再武装は「ユーザーがブレークポイントで停止した状態から、何らかの方法で実行を再開した瞬間」に自動的に働く。`arm_breakpoint_rearm` はヒット直後・`command_loop` に入る前に TF をセットするだけなので、ユーザーが `continue`/`si`/`step`/`n`/`up`/`run` のいずれで再開しても、最初の 1 命令（元の命令が復元された状態）を実行した時点で `STATUS_SINGLE_STEP` が発生し、そこで `0xCC` が再度書き込まれる。

- **`continue`/`up`/`run` の場合**: `next_mode`/`step_mode` が無効なので、再武装後は何もせず `break` してそのまま自由に実行を続ける。
- **`n`/`step` の場合**: `next_mode`/`step_mode` が有効なので、再武装後にもう一度 `single_step()` を呼んで `break` し、次の `STATUS_SINGLE_STEP` イベントで本来の行番号判定（5.2 節）へ処理を委ねる。
- **`si` の場合**: ユーザーが明示的に単独ステップを要求しているため、再武装の 1 ステップと `si` の 1 ステップが重なるこのケースだけは特別扱いが必要になる。`dbg->si_requested` フラグ（`si` コマンドでセット、`STATUS_SINGLE_STEP` 処理の先頭で読み取って即座にクリア）を見て、再武装ステップを静かに握りつぶさず、既存の単独ステップ表示処理（`step -> RIP=...` + ソース行表示 + `command_loop`）へフォールスルーさせる。

**マルチスレッド対応での他スレッド保護（v2.0）**: 元バイトを一時的に復元してから 1 命令だけ実行し `0xCC` を書き戻すまでの区間、他スレッドが同じアドレスを実行して `0xCC` の不在に気づかれずヒットを見逃してしまう競合状態がありうる。これを防ぐため、`arm_breakpoint_rearm()` を呼んだ直後に `suspend_other_threads()`（17.2 節）で他の全スレッドを一時停止し、`finish_breakpoint_rearm()` で `0xCC` を書き戻した直後に `resume_other_threads()`（17.2 節）で再開する。この一時停止区間は「ヒットしてから再武装が完了するまで」（ユーザーが `command_loop` で操作している間も含む）に限定され、`continue`/`step`/`next` の通常実行中は適用されないため、他スレッドとの待ち合わせによるデッドロックのリスクは無い。malloc/calloc/realloc/free のエントリフック（16.4 節）の再武装にも同じ保護を適用している。

## 8. レジスタ操作設計（registers.c）

- `show_registers`: `CONTEXT.ContextFlags = CONTEXT_FULL` を指定し `GetThreadContext` で取得。`_WIN64` 定義の有無で 64bit（RIP/RAX/RBX/RCX/RDX/RSI/RDI/RBP/RSP/R8/R9/R10/R11/R12/R13/R14/R15/RFL/ST0-ST7/XMM0-XMM15）と 32bit（EIP/EAX/EBX/ECX/EDX/ESP）の表示を切り替える。出力は「[General Purpose Registers]」ヘッダ下に 2 列で 64bit 汎用レジスタ（RIP/RAX〜R15/RFL）を、「[x87 FPU Registers]」ヘッダ下に ST0-ST7（80bit）を、「[XMM Registers]」ヘッダ下に XMM0-XMM15（128bit）を表示し、各セクション間に空行を挿入して見やすくしている。32bit ビルドでは「[General Purpose Registers]」ヘッダ下に 2 列で EIP/EAX/EBX/ECX/EDX/ESP を表示する。
- `single_step`: `CONTEXT.EFlags` に `0x100`（トラップフラグ／TF）を OR し `SetThreadContext` で書き戻す。次の 1 命令実行後に `STATUS_SINGLE_STEP` 例外が発生する。
- `set_register(dbg, name, value, fvalue, is_float)`: レジスタ名文字列（大文字小文字区別なし、`_stricmp`）を `CONTEXT` の対応フィールドへ振り分ける if-else チェーン。取得時は `CONTEXT_FULL | CONTEXT_FLOATING_POINT`。64bit レジスタ名（`rax`〜`r15`）は全体を上書き、32bit エイリアス（`eax`〜`eip`, `eflags`）は下位 32bit のみをマスク付きで書き換える。x64 では XMM0〜XMM15 に対して右辺整数値を下位 64bit に、ST0〜ST7 に対して浮動小数点リテラルを x87 80bit 形式に変換して書き込む。未知の名前は `0` を返し、呼び出し元（`commands.c` の `set` 処理）は変数代入へフォールバックする。

## 9. メモリ参照設計（memory.c）

- `examine_memory(dbg, addr)`: `ReadProcessMemory` で固定 16 バイトを読み取り、16 進数 2 桁区切りで出力する。読み取り失敗時のエラーメッセージは無く、未初期化バッファがそのまま表示される点に留意。

## 11. 逆アセンブラ設計（disasm.c）

### 11.1 全体方針

DbgHelp や外部逆アセンブルライブラリを使わず、x64 命令のバイト列を自前でデコードする最小限のディスアセンブラである。対応していない命令はオペコードのバイト列のみを `.byte 0xNN` または `op_NN <operand>` として表示する（完全なニーモニック対応ではない）。

### 11.2 デコード処理（`decode_one`）

1. プレフィックスループ: `0x40`〜`0x4F`（REX プレフィックス、W/R/X/B ビットを分解）、`0x66`（オペランドサイズ）、`0x67`（アドレスサイズ）を読み飛ばしながら記録。
2. 2 バイト opcode（`0x0F` 開始）: 条件分岐命令（`0x80`〜`0x8F` → `jcc rel32`）、`syscall`（`0x0F 0x05`）、`cpuid`（`0x0F 0xA2`）、`movzx`（`0x0F 0xB6`/`0xB7`）に対応。それ以外は `0f_XX` 表示。
3. `push`/`pop`（`0x50`〜`0x5F`）、`mov reg, imm`（`0xB8`〜`0xBF`、REX.W の有無で imm32/imm64 切替）、短形式 `jcc rel8`（`0x70`〜`0x7F`）。
4. 単純命令: `nop`(`0x90`), `ret`(`0xC3`), `ret imm16`(`0xC2`), `int3`(`0xCC`), `leave`(`0xC9`), `call rel32`(`0xE8`), `jmp rel32`(`0xE9`), `jmp rel8`(`0xEB`)。
5. ModRM を伴う命令（`has_modrm_1byte` に列挙されたオペコード群）: `decode_modrm` で ModRM/SIB／ディスプレースメントを解析しオペランド文字列を生成。`0x80/0x81/0x83`（ALU immediate: add/or/adc/sbb/and/sub/xor/cmp）、`0x89`/`0x8B`（`mov`）、`0x8D`（`lea`）、`0xC6`/`0xC7`（`mov r/m, imm`）、`0xFF`（`inc/dec/call/jmp/push` の拡張オペコード判定）を個別処理。それ以外は即値長を `imm_len_for_op` で判定してスキップしつつ `op_XX <operand>` として表示。
6. 上記いずれにも該当しないバイトは `.byte 0xNN` として 1 バイト消費する。

### 11.3 ModRM/SIB 解析（`decode_modrm`, `modrm_len`）

- `mod==3`: レジスタ直接（`reg_name` でレジスタ名を解決）。
- `rm==4`（SIB あり）: SIB バイトを読み取り、簡易実装として **base/index/scale は解析するが最終的な表示には反映せず、`[rsp+disp]` 固定表記**としている（実装上の簡略化点）。
- `mod==0 && rm==5`: RIP 相対（`[rip+disp32]`）。
- それ以外: `mod` に応じたディスプレースメント長（0/1/4 バイト）を読み取り `[reg+disp]` 形式で表示。

### 11.4 表示処理（`disassemble_at`）

1. 対象範囲（最大 256 バイト）内に設定済みの恒久／一時ブレークポイントが存在する場合、表示のために元バイトへ一時的に書き戻し、`FlushInstructionCache` を実行する。
2. `ReadProcessMemory` で命令バイト列を読み取る。
3. 手順 1 で書き戻したブレークポイントを、読み取り後に `0xCC` へ再度書き戻す（実行状態を変えずに正しい逆アセンブル結果を得るための退避・復元処理）。
4. `decode_one` を繰り返し呼び出し、指定命令数（既定 10）に達するかバッファ終端まで、アドレス・生バイト列・ニーモニックを整形して表示する。

## 12. 式評価器設計（expr.c / `expr_parser.y` / `expr_lexer.l`）

**v1.9 で全面改訂**: 従来は `expr.c` 内の手書き字句解析（`lex_advance`）＋再帰下降パーサ（`parse_primary`〜`parse_logor`、`try_parse_typename`）で式を解析していた。v1.9 でこの部分を bison/flex 生成の文法（`expr_parser.y`/`expr_lexer.l`）へ置き換えた。シンボル・メンバ解決（`expr_lookup_symbol`/`lookup_member`）、値の読み書き（`load_lvalue`）、評価結果の表示・代入（`expr_print_fmt`/`expr_assign`）は従来通り `expr.c` に残っており、`expr_internal.h` を介して文法アクションから呼び出す。公開 API（`expr_eval`/`expr_print_fmt`/`expr_print`/`expr_assign`、`expr.h`）に変更は無い。

### 12.1 文法（優先順位の低い順、`expr_parser.y`）

```
expr        := logand ( '||' logand )*
logand      := bitor  ( '&&' bitor )*
bitor       := bitxor ( '|'  bitxor )*
bitxor      := bitand ( '^'  bitand )*
bitand      := eq     ( '&'  eq )*
eq          := rel    ( ('=='|'!=') rel )*
rel         := shift  ( ('<'|'>'|'<='|'>=') shift )*
shift       := add    ( ('<<'|'>>') add )*
add         := mul    ( ('+'|'-') mul )*
mul         := unary  ( ('*'|'/'|'%') unary )*
unary       := ('*'|'&'|'-'|'+'|'~'|'!') unary | '(' typename ')' unary | postfix
postfix     := primary ( '[' expr ']' | '.' ident | '->' ident )*
primary     := NUM | ident | sizeof '(' typename ')' | sizeof '(' expr ')' | '(' expr ')'
```

各段は旧実装の対応する `parse_XXX` 関数と 1 対 1 に対応する非終端記号（`logand_expr`/`bitor_expr`/…/`unary_expr`/`postfix_expr`/`primary_expr`）として文法に書き下してあり、bison の演算子優先順位宣言（`%left` 等）は使わず段ごとの文法規則のみで優先順位を表現している。

**キャストの結合位置についての設計変更**: 旧実装では `(型名)expr` のオペランドを `parse_assign_expr`（文法上の最上位＝式全体）まで貪欲に読み進めていたため、`(int)a + b` が `(int)(a + b)` として評価されていた（C 言語の意味論では `((int)a) + b` が正しい）。この挙動をそのまま bison 文法に写す（`primary: '(' typename ')' expr` のように未括弧の `expr` をキャスト規則へ埋め込む）と、あらゆる優先順位段の境界で「キャストのオペランドをさらに読み進めるか、キャスト規則を還元するか」という shift/reduce 衝突が発生する（実装過程で 53 件検出。bison の既定動作である shift 優先で衝突自体は解消されるが、文法として本質的に曖昧である）。C 言語の実際の文法（`cast-expression : unary-expression | '(' type-name ')' cast-expression`）に合わせ、キャストを `unary_expr` の一形態（オペランドは `unary_expr`）として定義し直すことで衝突を構造的に解消するとともに、`(int)a + b` が `((int)a) + b` として評価されるよう修正した（挙動変更）。

`sizeof(型名)` と `sizeof(式)`、`(型名)expr` の C 言語キャストに対応する点は変わらない。型名として解釈できるかどうかは、下記 12.2 節の字句解析側でのトークン分類により一意に決定され、旧実装のようなバックトラックは不要になった。

### 12.2 字句解析（`expr_lexer.l`）

数値（16 進数 `0[xX][0-9a-fA-F]+`、8 進数 `0[0-7]*`、10 進数 `[1-9][0-9]*`、小数点付き浮動小数点数）、識別子、文字リテラル（`'A'`/`'\n'` 等のエスケープ含む）、2 文字演算子（`->`, `<<`, `>>`, `&&`, `||`, `==`, `!=`, `<=`, `>=`）、1 文字演算子（`+ - * / % & | ^ ~ ! ( ) [ ] . < > ,`）をトークン化する。未知の文字は専用の規則がエラーメッセージを記録したうえでその文字自身を返し、以後は bison 側の構文エラーとして扱われる。

`sizeof` は予約語として `SIZEOF` トークンを、`char`/`short`/`int`/`long`/`float`/`double`/`void`/`unsigned`/`signed`/`size_t`/`ptrdiff_t`/`DWORD`/`DWORD64`/`BYTE`/`WORD`/`QWORD`（旧 `builtin_type_size` と同じ語彙）は `TYPEWORD` トークンを、それ以外の識別子は `IDENT` トークンを返す。この字句解析段階での分類により、`(` の直後のトークンが `TYPEWORD` か否かだけで「キャスト」か「括弧式」かが文法上一意に決まり、旧実装の `try_parse_typename` が行っていたバックトラックが不要になっている。

### 12.3 型名解析（`typename` 規則、`expr_parser.y`）

`typename_words: TYPEWORD | TYPEWORD TYPEWORD | TYPEWORD TYPEWORD TYPEWORD` という規則で最大 3 語まで連結し（旧 `try_parse_typename` の「1〜3 語先読み」と同じ上限）、結合した文字列（および先頭 1 語のみの文字列）の両方を `builtin_type_size()`（`expr.c`、変更無し）に渡して、まず結合形が既知の型名に一致するか、一致しなければ先頭 1 語のみで一致するかを判定する。末尾の `*` はポインタとして扱い、サイズを 8 バイト固定にする。字句解析側で `TYPEWORD` として分類されるのは既知の型キーワードのみであるため、`typename_words` が誤って通常の識別子を消費することは無く、旧実装のようなバックトラックは発生しない。

### 12.4 シンボル解決（`expr_lookup_symbol`、`expr.c`）

まず `SymEnumSymbols(dbg->sym_handle, 0, "*", ...)` で全シンボルを走査し名前一致するものを探す。この呼び出しは `BaseOfDll=0` のため現在のスコープ（ローカル変数・引数）しか列挙できない。

- `SYMFLAG_REGREL`（RSP/RBP 相対のローカル変数）: `CV_AMD64_RSP`(335)/`CV_AMD64_RBP`(334) の判定でベースレジスタを選び、オフセットを加算してアドレスを算出。
- `SYMFLAG_REGISTER`（レジスタ変数）: `si->Register` の CodeView レジスタ番号（`CV_AMD64_RAX`=328 等、32bit サブレジスタ含む）を `CONTEXT` の該当フィールドへマッピングして値を直接取得する。この場合 `out_size = 0` を返し、呼び出し元でメモリ実体を持たない「レジスタ変数」として扱う。
- それ以外（グローバル等）: `si->Address` をそのままアドレスとして使用。

**不具合修正（v1.6）**: 上記の `SymEnumSymbols` ベースの探索では、ローカル変数・引数は見つかるが**真のグローバル変数（例: `g_counter`）が一切見つからなかった**（`print g_counter`/`set g_counter=...` が常に `symbol 'g_counter' not found` になる不具合）。原因は `SymEnumSymbols(hProcess, 0, mask, ...)` が現在のスコープの局所シンボルしか列挙せず、グローバルデータシンボルまで到達しないことであった。`SymEnumSymbols` で見つからなかった場合、`SymFromName(dbg->sym_handle, name, ...)`（`lookup_symbol`（symbols.c）が関数名解決に使っているのと同じ API で、実際に `malloc`/`free`/`factorial` 等の解決実績がある）へフォールバックするよう修正し、グローバル変数への直接アクセスを可能にした。

**不具合修正（v1.7、`show globals` の一覧表示）**: v1.6 時点ではモジュール実ベースアドレスを渡す `SymEnumSymbols(hProcess, mod_base, "*", ...)` を試しても、静的リンクされた CRT 側のグローバル変数は列挙されるのに対しユーザー自身のコンパイランドが定義した関数・グローバル変数が一切列挙結果に現れず、原因不明として据え置いていた。実際の原因は `SymEnumSymbols` そのものではなく、そのコールバック（`show_enum_cb`, 10.8 節）が列挙の最中に `expr_print()` を呼び、`expr_print` が内部で `expr_lookup_symbol` を経由して**同じ `dbg->sym_handle` に対し `SymEnumSymbols` を再度呼び出していた**ことだった。DbgHelp の列挙 API はこの種の再入に対して安全ではなく、外側の列挙が想定より早期に打ち切られていた。列挙中は名前の収集のみに留め、列挙が完全に終わってから `expr_print()` をまとめて呼ぶよう `show_variables`/`show_enum_cb`（10.8 節）を修正し、モジュール全体の列挙が正しく機能することを確認した。

### 12.5 メンバ・添字アクセス（`do_index`/`do_member`、`expr_parser.y`）

旧 `parse_postfix` のループ本体を、`postfix_expr` 文法規則の各アクションから呼ぶ `do_index()`（`[]`）・`do_member()`（`.`/`->`）という 2 つの関数に分割した以外、ロジックは変更していない。

- `[]`: 対象が `SYM_TAG_POINTER` ならポインタの値をベースアドレスとして使用、`SYM_TAG_ARRAYTYPE` なら現在のアドレスを起点として要素サイズ分オフセットする。それ以外は `subscript requires array or pointer` エラー。
- `.`/`->`: `->` の場合はまずポインタの指し先アドレスへ切り替えたうえで、`lookup_member`（`TI_FINDCHILDREN`＋`TI_GET_SYMNAME`一致判定）でメンバのオフセット・型を取得する。

### 12.6 型名の解決（`get_type_name` / `udt_kind_prefix` / `basetype_name`）

`print pretty on` 時に各値へ付与する `(型名)` 注記（例: `(int)`, `(char *)`, `(int [5])`, `(struct test_struct)`）を組み立てる処理。

- `get_type_name(dbg, modbase, type_id, buf, buflen)`: `TI_GET_SYMTAG` の値により再帰的に型名を構築する。
  - `SYM_TAG_POINTER`: `TI_GET_TYPEID` で指し先の型を取得し、`get_type_name` を再帰呼び出しした結果に `" *"` を付加する（解決できない場合は `"void *"`）。
  - `SYM_TAG_ARRAYTYPE`: 要素型を再帰的に名前解決し、`TI_GET_LENGTH`（配列全体）と要素の `TI_GET_LENGTH` から要素数を算出して `"要素型名 [要素数]"` の形式にする。
  - `SYM_TAG_BASETYPE`: `TI_GET_BASETYPE`（DbgHelp `BasicType` 列挙値）と `TI_GET_LENGTH`（バイト長）を `basetype_name()` に渡し、`int`/`char`/`unsigned int`/`float`/`double`/`bool`/`long` 等の C 型名文字列に変換する。
  - それ以外（UDT／Enum／Typedef 等、名前を持つ型）: 従来通り `SymGetTypeInfo(TI_GET_SYMNAME)` でシンボル自身の名前を取得する。
- `udt_kind_prefix(dbg, modbase, type_id)`: `SymGetTypeInfo(..., TI_GET_UDTKIND, &kind)` で UDT の種別（`UdtStruct`=0 / `UdtClass`=1 / `UdtUnion`=2 / `UdtInterface`=3）を取得し、`UdtUnion` なら `"union "`、それ以外は `"struct "` を返す。`print_val`／`expr_print_fmt` の UDT 表示箇所で型名の直前に付与される。
- **不具合修正（v1.1）**: 上記の型名解決を実装する過程で、型タグ定数 `#define SYM_TAG_BASETYPE 2`（v1.9 以降は `expr_internal.h` で定義）が誤りであることが判明した。DbgHelp の実際の `SymTagBaseType` 値は `16`（`2` は `SymTagCompiland` に相当）であり、この誤りにより基本型（int/char 等）の型名解決が常に失敗していた（既存の char 判定ロジックは `TI_GET_LENGTH==1` 等の副次条件で偶然動作していたため、これまで症状が表面化していなかった）。`SYM_TAG_BASETYPE` の値を `16` に修正済み。

### 12.7 表示処理（`expr_print_fmt` / `print_val` / `print_struct_ex`）

評価結果の型タグ（`TI_GET_SYMTAG`）に応じて表示形式を切り替える。

| 型タグ | 表示内容 |
|---|---|
| `SYM_TAG_ARRAYTYPE` | 既定書式時は要素を入れ子表示（`print_pretty` により複数行/1 行を切替）、明示書式時は各要素へフォーマットを適用して展開表示 |
| `SYM_TAG_UDT`（構造体／共用体） | メンバを再帰的に展開表示（`print_struct_ex`、`print_pretty` により改行有無を切替）。`print_pretty` が有効な場合、型名の前に `udt_kind_prefix()` の結果（`struct `／`union `）を付与する。メンバ自身が UDT の場合（ネスト構造体）も `print_val` を再帰的に通るため同じ注記が適用される |
| `SYM_TAG_POINTER` | 文字ポインタ（typedef 解決後 `btChar`/`btWChar` 相当、またはサイズ 1）と判定できる場合はアドレス＋文字列内容を表示。それ以外はアドレスを 16 進表示、明示的な `/d /o /t /c` 指定時は数値としてのフォーマットを適用 |
| スカラ | `char` 相当と判定できれば文字表示、それ以外は符号付き整数＋16 進数の併記。フォーマット指定時は `print_int_fmt` に委譲 |

いずれの場合も `print_pretty` が有効なときのみ `get_type_name()` で型名を取得し `(型名)` 注記を付与する（`print_pretty` 無効時は型名注記自体を行わない）。

`/s` 指定時は型タグに関わらず値をポインタとみなし NULL 終端文字列として読み出し表示する（`print_string_fmt`）。

**不具合修正（v1.1・非整形モードの余分な空白）**: `print_val` はメンバのネスト深さ（`depth`）に応じたインデント文字列 `indent`（半角スペース 2 個 × depth）を計算していたが、従来は `print_pretty` の値に関わらず常に計算・付与していたため、`print pretty off` の 1 行表示でもメンバラベルの前に無駄な空白が混入していた（例: `s = {   a = 1 (0x1),   b = 2 (0x2) }` のような多重スペースや、ネスト構造体でのインデント重複）。`indent` の計算を `if (dbg->print_pretty)` でガードし、非整形モードでは常に空文字列（インデントなし）となるよう修正した。修正後は `s = { a = 1 (0x1), b = 2 (0x2) }` のように単一スペースのみとなる。

**不具合修正（v1.7・配列/構造体メンバ読み取り時のスタックバッファオーバーフロー）**: `print_struct_ex`（メンバ読み取り）と `expr_print_fmt` の配列表示 2 系統・4 箇所（`FMT_DEFAULT`/明示フォーマット × pretty/非 pretty）はいずれも、要素またはメンバの型の `TI_GET_LENGTH`（`child_len`/`elem_len`）をそのまま `ReadProcessMemory` の読み取りサイズとして渡し、`unsigned long long val`（8 バイト固定）へ読み込んでいた。`show globals` のモジュール全体列挙で到達するようになった CRT 内部変数の中に、配列要素の型情報が入れ子構造になっているなどの理由で `TI_GET_LENGTH` が 8 バイトを超える値を返すものがあり（`_mbctypes` 等）、`ReadProcessMemory` が `val` の領域を超えて書き込むスタックバッファオーバーフローが発生し、`/RTC1`（デバッグビルドのランタイムチェック）に検知されて `abort()` が呼ばれ windbg 自身がクラッシュしていた（`show globals`/`print _mbctypes` 単体で再現）。該当 5 箇所すべてで `read_len = min(child_len または elem_len, sizeof(val))` にクランプしてから `ReadProcessMemory` を呼ぶよう修正した。

### 12.8 代入処理（`expr_assign`）

`expr_eval` で左辺を評価し、`is_lvalue` でなければ `'%s' is not assignable` エラー。lvalue の場合、バイトサイズ（4 以下は 32bit 切り詰め、それ以外は 64bit）で `WriteProcessMemory` により書き込む。

## 13. コマンド⇔内部処理 対応表（代表例の詳細トレース）

### 13.1 `break foo`（シンボル名指定）

1. `sscanf_s` で `foo` を抽出。
2. `:` を含まず `0x` 始まりでもないため `lookup_symbol(dbg, "foo")` を実行 → `SymFromName` でアドレス解決。
3. アドレスが得られたら `skip_function_prologue()` で最初の実行可能行へ補正。
4. `set_breakpoint()` で当該アドレスに `0xCC` を書き込み、`breakpoint_t` をリストへ追加。

### 13.2 `p/x s.a`（構造体メンバの 16 進表示）

1. `commands.c` の `print`/`p` 分岐で `/x` を検出し `fmt = FMT_HEX`、残り文字列 `s.a` を `expr_buf` へ格納。
2. `expr_print_fmt(dbg, "s.a", FMT_HEX)` → `expr_eval`（内部で `expr_parse`、`expr_parser.y` の `postfix_expr` 規則）が `s`（`expr_lookup_symbol` でローカル変数解決）→ `.` → メンバ `a` を `do_member`/`lookup_member` で解決し、オフセット加算後 `load_lvalue` で値読み出し。
3. 型タグはスカラ（`int`）のため `print_int_fmt` で `0x...` 形式に整形して出力。

### 13.3 `x rsp+8`

1. `commands.c` の `x` 分岐で `rsp+` 接頭辞を検出し、`atoi(arg+3)` でオフセット `8` を取得。
2. `GetThreadContext` で現在の `Rsp` を取得し `addr = ctx.Rsp + 8` を算出。
3. `examine_memory(dbg, (void*)addr)` が 16 バイトを読み取り 16 進ダンプ表示。

### 13.4 `show bp`（ブレークポイント一覧）

1. `commands.c` の `show ` 分岐で引数文字列を抽出し `strcmp(what, "bp") == 0` を判定。
2. 一致する場合は `show_variables()` を呼ばず `print_breakpoints(dbg)`（breakpoints.c, 7.3 節）を呼ぶ。
3. `dbg->breakpoints` を先頭から走査し、各ブレークポイントのアドレスに対して `SymFromAddr`（関数名＋オフセット）と `SymGetLineFromAddr64`（ファイル名＋行番号）を解決してインデックス付きで 1 行ずつ出力する。

### 13.5 `print s`（構造体、`print pretty on`）

1. `commands.c` の `print`/`p` 分岐で式文字列 `s` を `expr_print_fmt(dbg, "s", FMT_DEFAULT)` に渡す。
2. `expr_eval` が `s`（ローカル変数）を解決し、型タグ `SYM_TAG_UDT` の `expr_val_t` を返す。
3. `dbg->print_pretty` が有効なため `get_type_name()` で型名 `test_struct` を取得し、`udt_kind_prefix()` で `struct` を判定して `s = (struct test_struct) {` を出力。
4. `print_struct_ex()` が各メンバ（`a`, `b`）について `print_val()` を呼び、メンバごとに `get_type_name()` でスカラ型名 `int` を解決して `  a = (int) 1 (0x1)` のように型名付きで出力する。
5. 閉じ括弧 `}` を出力して終了する。

## 14. エラー処理・ログ方針

- 多くの Win32 API 呼び出し（`ReadProcessMemory`/`WriteProcessMemory`/`FlushInstructionCache` 等）の戻り値は明示的にチェックされておらず、失敗時も後続処理がそのまま進む箇所が複数存在する（例: `examine_memory` は読み取り失敗時も `buf` の内容をそのまま表示する）。
- 式評価器（`expr.c`／`expr_parser.y`）はエラーを `expr_val_t.errmsg`（文法アクション内で生成される個別のエラー値）または字句解析・構文解析エラー用のグローバル状態 `expr_parse_err`/`expr_parse_errmsg`（`expr_internal.h`）に格納し、`expr_parse()` がいずれかを `expr_val_t.errmsg` へ統一して呼び出し元へ伝搬する。`command_loop` は `printf("error: %s\n", ...)` でユーザーに通知する。この部分は比較的一貫したエラー処理になっている。
- `symbols.c` の未使用（死んだ）コード `print_struct` に開発時調査用の `fprintf(stderr, "[debug] print_struct ...")` が残置されている。標準エラー出力のため通常のコンソール表示（標準出力）とは分離されるが、実行経路が無いため実害は無い。`print_symbol_info`/`syms_enum_cb`（`syms` コマンド）にあった `[SYMS] ...` ログは v1.8 で削除済み。

## 16. メモリリーク検出設計（leakcheck.c）

### 16.1 全体方針

`malloc`/`calloc`/`realloc`/`free` のエントリアドレスに恒久的な `0xCC` を書き込み、ヒットするたびに引数（x64 Microsoft ABI: 第1引数は RCX、第2引数は RDX）を読み取ってから、対象アドレスの元バイトを一時的に復元して 1 命令だけシングルステップさせ、その直後に `0xCC` を書き戻す（再武装）。この「復元→単独ステップ→再武装」を挟むことで、既存の `breakpoints.c` の一発ブレークポイント（ヒット後に元バイトを復元したまま二度と `0xCC` を書き戻さない設計、7.1 節参照）とは異なり、同一アドレスに何度でもヒットさせられる。

この復元→再武装の手当てを忘れると、ブレークポイントで停止した RIP をそのまま巻き戻して実行再開した場合、CPU は同じ `0xCC` を即座に再実行し `EXCEPTION_BREAKPOINT` が同一アドレスで無限に発生し続ける（本機能の実装初期に実際に発生し、`testprog.exe` が応答不能になることで発覆した不具合）。

`malloc`/`calloc`/`realloc`/`free` のブレークポイントは `breakpoints.c` の `dbg->breakpoints` 連結リスト（`set_breakpoint`/`show bp` が扱う一覧）とは別管理とし、`debugger_t` 専用フィールド（`malloc_addr`/`malloc_orig_byte` 等、2.1 節）で直接バイトを読み書きする。これにより `show bp` にはユーザー設定のブレークポイントのみが表示され、内部計装用のブレークポイントとは混同されない。

### 16.2 有効化・無効化

- `leak_tracking_enable(dbg)`: `lookup_symbol(dbg, "malloc")`/`"calloc"`/`"realloc"`/`"free"`（symbols.c）でアドレスを解決する。`malloc` と `free` は必須、`calloc` と `realloc` はオプション。解決できなければ「対象が CRT を静的リンクしている必要がある」旨のメッセージを出して失敗する。解決できれば各アドレスの元バイトを読み取って保存し、`0xCC` を書き込んで `leak_tracking=1` にする。
- `leak_tracking_disable(dbg)`: `malloc_addr`/`calloc_addr`/`realloc_addr`/`free_addr` の元バイトを直接書き戻す（`leak_tracking_enable` 時点の状態に関わらず冪等）。進行中の `malloc_ret_addr`（16.3 節）や `leak_rearm_addr`（16.4 節）が残っていればそれぞれ後始末したうえでクリアし、`allocations` 連結リストを全解放する。

### 16.3 確保関数の引数・戻り値の捕捉

- `leak_on_alloc_enter(dbg, addr, func_name)`: 共通の確保関数エントリ処理。`ctx.Rcx` から第1引数を、`ctx.Rdx` から第2引数を取得。`calloc` の場合は `count * size` を計算して `pending_alloc_size` に保存。確保関数名を `current_alloc_func` に記録。リターンアドレスに一時ブレークポイントを設定し、16.4 節の再武装処理を呼ぶ。
- `leak_on_malloc_enter(dbg)`: `malloc` エントリヒット時に `leak_on_alloc_enter(dbg, dbg->malloc_addr, "malloc")` を呼ぶ。
- `leak_on_calloc_enter(dbg)`: `calloc` エントリヒット時に `leak_on_alloc_enter(dbg, dbg->calloc_addr, "calloc")` を呼ぶ。
- `leak_on_realloc_enter(dbg)`: `realloc` エントリヒット時に `leak_on_alloc_enter(dbg, dbg->realloc_addr, "realloc")` を呼ぶ。
- `leak_on_malloc_return(dbg)`: 確保関数リターン時に呼ばれる。元バイトを復元し `malloc_ret_addr` をクリアした後、`ctx.Rax`（戻り値ポインタ）が非 NULL であれば `{addr=Rax, size=pending_alloc_size, caller=ctx.Rip, alloc_func=current_alloc_func}` を `allocations` の先頭へ追加する。
- `leak_on_free_enter(dbg)`: `free` エントリヒット時に呼ばれる。`ctx.Rcx`（解放対象ポインタ）が `allocations` 内に見つかればそのノードを削除する（NULL や未追跡ポインタは黙って無視）。最後に 16.4 節の再武装処理を `free_addr` に対して呼ぶ。

### 16.4 再武装（`rearm_after_one_step` / `leak_finish_rearm`）

- `rearm_after_one_step(dbg, addr, orig_byte)`（leakcheck.c 内部静的関数）: `addr` に `orig_byte`（本来の命令バイト）を書き戻し、`CONTEXT.EFlags` に TF（`0x100`）を立てて 1 命令だけ実行されるようにし、`dbg->leak_rearm_addr`/`leak_rearm_byte` に記録する。
- `leak_rearm_pending(dbg)` / `leak_finish_rearm(dbg)`: `debugger.c` 側から呼ばれる公開 API。`leak_rearm_addr` が非 NULL かどうかを問い合わせ、`STATUS_SINGLE_STEP` 発生時に `0xCC` を書き戻して `leak_rearm_addr` をクリアする。

### 16.5 debugger.c との連携（5.3.1 節参照）

`EXCEPTION_BREAKPOINT` 発生時、ヒットアドレスが `malloc_addr`/`calloc_addr`/`realloc_addr`/`free_addr`/`malloc_ret_addr` のいずれかであれば対応する関数を呼んで `command_loop` を呼ばずに `break` する（サイレント計装）。`STATUS_SINGLE_STEP` 発生時は `leak_rearm_pending(dbg)` をチェックし、保留中であれば `leak_finish_rearm(dbg)` で再武装したうえで、ユーザーの `next_mode`/`step_mode` が同時に有効な場合のみ `single_step()` を呼び直して継続させる（そうでなければそのまま `break` して静かに実行再開する）。この「同時に有効なら single_step を呼び直す」処理により、リーク追跡用の内部シングルステップが `next`/`step` の行番号判定ループを飢餓状態にする（TF が落ちたまま誰も再開させず、事実上フリーランする）ことを防いでいる。

**v1.5 での判定順序**: `STATUS_SINGLE_STEP` 処理では `breakpoint_rearm_pending(dbg)`（通常ブレークポイントの再武装、7.4 節）を `leak_rearm_pending(dbg)` より先にチェックする。両者が同時に保留になる状況（ユーザーが `malloc`/`free` のエントリアドレスそのものに恒久ブレークポイントを張るような、意図的でない限り起こらないケース）は考慮していない。

### 16.6 `show leaks` / 終了時レポート（`print_leaks`）

`print_breakpoints`（`show bp`, 7.3 節）と同じ手法で、`allocations` の各要素について `SymFromAddr`＋`SymGetLineFromAddr64` により `caller`（確保関数呼び出し元アドレス）を「関数名+オフセット at file:line」に整形し、確保アドレス・サイズ・確保関数名（malloc/calloc/realloc）と共に一覧表示する。末尾に件数・合計バイト数のサマリを付与する。`leak_tracking` が無効な場合や `allocations` が空の場合はそれぞれ専用のメッセージを表示する。この関数は `show leaks` コマンド、および `EXIT_PROCESS_DEBUG_EVENT`（`leak_tracking` 有効時、5.3 節）の双方から呼ばれる。

## 17. マルチスレッド管理設計（threads.c、v2.0）

### 17.1 スレッドレジストリ

- `thread_entry_t`（2.2.3 節）の単方向連結リスト（先頭挿入）を `dbg->threads` として保持する。
- `register_thread(dbg, tid, handle)`: ノードを `malloc` し、`tid`/`handle` を設定してリスト先頭へ挿入する。`CREATE_PROCESS_DEBUG_EVENT`（メインスレッド、5.1 節）と `CREATE_THREAD_DEBUG_EVENT`（以降生成されるスレッド、5.1.1 節）の双方から呼ばれる。
- `unregister_thread(dbg, tid)`: リストから該当ノードを取り外し、`CloseHandle(handle)` を呼んでから `free()` する。`EXIT_THREAD_DEBUG_EVENT`（5.1.2 節）から呼ばれる。メインスレッド由来のハンドル（`CreateProcessA` の `pi.hThread`）と `CREATE_THREAD_DEBUG_EVENT` 由来のハンドル（`ev.u.CreateThread.hThread`）を区別せず、どちらも同じ経路で `CloseHandle` する（後者は Win32 デバッグ API がデバッガ用に払い出す専用ハンドルであり、明示的なクローズが必要）。
- `find_thread_handle(dbg, tid)`: リストを線形探索し、`tid` が一致するノードの `handle` を返す（見つからなければ `NULL`）。`debugger.c` の `EXCEPTION_DEBUG_EVENT` 処理（5.2 節）や `commands.c` の `do_thread`（17.3 節）から呼ばれる。
- `free_all_threads(dbg)`: リストのノードのみを解放する（`CloseHandle` は呼ばない）。`debugger_restart`（4.2 節）専用。対象プロセスが終了済み／終了処理中である前提のため、既存の `dbg->process`/`dbg->thread` を再起動時に明示的にクローズしない従来の方針に合わせている。
- `print_threads(dbg)`: リストを走査し、各 `tid` を 1 行ずつ表示する。`dbg->tid` と一致する行には `(current)`、さらに `dbg->locked_tid` とも一致する場合は `(current, locked)` を付記する（`show threads` コマンド用）。

### 17.2 他スレッドの一時停止／再開

- `suspend_other_threads(dbg)` / `resume_other_threads(dbg)`: `dbg->threads` を走査し、`tid != dbg->tid` の全ノードに対して `SuspendThread`/`ResumeThread` を呼ぶ。
- 呼び出し元（`debugger.c`）は、ソフトウェアブレークポイント（恒久ブレークポイント・malloc/calloc/realloc/free エントリフック）の再武装区間（元バイトを一時的に復元してから 1 命令実行し `0xCC` を書き戻すまで）でのみ、この対を厳密に 1 回ずつ呼ぶ。この呼び出しパターンにより、`SuspendThread`/`ResumeThread` のサスペンドカウントがずれる（多重サスペンドや呼び忘れ）ことはない。詳細は 7.4 節（実際の掲載箇所はブレークポイント章、8 章）・16.5 節参照。

### 17.3 フォーカス自動固定（`dbg->locked_tid`）

- `dbg->locked_tid`（2.1 節）は「フォーカス固定先の TID」を表し、0 は未固定を意味する。
- `debugger.c` の `EXCEPTION_DEBUG_EVENT` 処理（5.2 節）先頭で `auto_continue = (dbg->locked_tid != 0 && dbg->tid != dbg->locked_tid)` を計算する。真であれば、トラッキング済みブレークポイント・ウォッチポイント・ステップ着地の各分岐は詳細表示と `command_loop` 呼び出しを省略し、1 行の通知のみを表示して自動継続する。
- 実際に表示・停止する分岐（トラッキング済みブレークポイントヒット、ウォッチポイントヒット、ステップ着地）は、表示する直前に `dbg->locked_tid = dbg->tid` を設定してフォーカスを（再）固定する。これにより、**最初に実際に停止したスレッドが自動的にアンカーとなり**、以後は他スレッドの同種の停止要因が自動継続される。未トラッキングのブレークポイント（起動直後の ntdll 初期停止など）や Ctrl+C 割り込みはこの判定・固定処理の対象外とし、常に表示・停止する（起動直後の一度きりの停止がそのまま恒久的なフォーカス固定として扱われてしまうのを避けるため）。
- `commands.c` の `do_thread(dbg, arg)`（`thread` コマンド）:
  - 引数が `lock`: `dbg->locked_tid = dbg->tid` を設定し、現在のスレッドへ明示的に固定する。
  - 引数が `unlock`: `dbg->locked_tid = 0` を設定し、固定を解除する（次に実際に停止したスレッドで自動的に再固定される）。
  - それ以外（TID 指定）: `strtoul(arg, NULL, 0)` で TID を解釈し、`find_thread_handle()` で存在確認したうえで `dbg->tid`/`dbg->thread` をそのスレッドへ切り替え、同時に `dbg->locked_tid` も更新する（明示的なフォーカス切替は「以後このスレッドを見続けたい」という意思表示とみなす）。
- `EXIT_THREAD_DEBUG_EVENT`（5.1.2 節）で `dbg->locked_tid` が終了するスレッドの TID と一致する場合、固定を解除する（0 にする）。解除しなければ、以後どのスレッドも「フォーカス外」と判定され続け、実質的に対話プロンプトへ戻れなくなるため。

### 17.4 既知の制約

- **スレッド生成通知の到達タイミング**: `CREATE_THREAD_DEBUG_EVENT` は `CreateThread()` がその呼び出し元へ制御を返すことと厳密には同期しておらず、OS 側の内部処理タイミング次第で通知の到達が遅れることがある（要件定義書 8 章参照）。
- **`up` のリターンアドレス取得の制約**: マルチスレッド対応スコープ外の既存不具合として、`do_up` が停止直後の `RSP` をそのままリターンアドレスとして読む実装になっており、`break` の既定のプロローグスキップと組み合わさるとローカル変数を持つ関数で誤ったアドレスを読んでしまう（要件定義書 8 章参照）。
- **リーク追跡の確保関数リターン待ちは 1 スロットのみ**: 16.5 節・上記マルチスレッド対応注記を参照。

## 18. マルチプロセス管理設計（processes.c、v3.0）

### 18.1 プロセスレジストリと「スワップ」方式

`debugger_t` の大半のフィールド（`breakpoints`/`sym_handle`/`watchpoints[4]`/`watch_count`/`threads`/リーク追跡関連一式/ステップ実行状態など、2.1 節末尾の一覧参照）は、実装上「本当は」プロセスごとに独立しているべき状態である。子プロセスは独自のアドレス空間・独自のモジュール（PDB）・独自のブレークポイントを持つ。素直に実装するなら `process_entry_t *cur_proc` を導入し、`dbg->breakpoints` のようなあらゆる参照箇所（breakpoints.c/watchpoints.c/leakcheck.c/commands.c/symbols.c/debugger.c の 100 箇所超）を `dbg->cur_proc->breakpoints` へ書き換える必要があるが、これは振る舞いを何も変えないまま大量の機械的な変更を要求するだけであり、コストに見合わない。

代わりに採用したのが「スワップ」方式である: 上記フィールド群は今まで通り `debugger_t` に置いたまま変更しない。`debugger_t` のこれらのフィールドは常に「現在アクティブなプロセス」のものを表す、という約束事だけを新設する。新設の `process_entry_t`（2.2.4 節、processes.c/h）は、現在アクティブでない各プロセスについて、この同じフィールド一式の**退避コピー**を保持する。

- **`switch_active_process(debugger_t *dbg, DWORD pid)`**: 指定 `pid` が既にアクティブなら何もしない。そうでなければ、(1) `debugger_t` の現在の状態一式を新しい `process_entry_t` としてまるごとコピーし `dbg->processes`（バックグラウンドリスト）の先頭へ push する、(2) `pid` に一致する `process_entry_t` をバックグラウンドリストから探して pop する、(3) その `process_entry_t` の保持していた状態一式を `debugger_t` へまるごとコピーする、(4) `dbg->pid`/`dbg->process` を更新する。`dbg->tid`/`dbg->thread` は意図的にクリアしたままにし、呼び出し元（5.2 節の `EXCEPTION_DEBUG_EVENT` 処理、あるいは `do_process` コマンド）がそれぞれの文脈でフォーカスを再設定する。
- **`register_new_process(debugger_t *dbg, DWORD pid, HANDLE handle)`**: ゼロ初期化した新規の `process_entry_t` をバックグラウンドリストへ push するのみで、アクティブにはしない（新規スレッド登録時と同じ「フォーカスを奪わない」方針、5.1.1 節参照）。
- **`unregister_process(debugger_t *dbg, DWORD pid, DWORD exit_code)`**: `process exited id=<PID> exit code=<code>` を表示する（`leak_tracking` が有効だったプロセスならリーク一覧も表示）。`pid` がバックグラウンドの（非アクティブな）プロセスであれば、そのノードをリストから外して `CloseHandle` し、`free()` する。`pid` がアクティブなプロセスであれば、ブレークポイント・確保情報・スレッド一覧などのそのプロセス固有のリソースを解放し、`dbg->locked_tid` が終了するプロセスに属するスレッドを指していれば解除する。バックグラウンドリストに他のプロセスが残っていれば、その先頭を pop して新しいアクティブプロセスへ昇格させる。戻り値は「まだ追跡中のプロセスが残っているか」の真偽値（5.3 節の `debugger_loop` 側の分岐に使う）。
- **`find_process_handle`/`find_background_process`**: それぞれ「PID からプロセスハンドルを引く」「PID からバックグラウンドリストの `process_entry_t` を引く」ための線形探索ヘルパー。後者は 5.1.1 節・5.1.2 節（`CREATE_THREAD_DEBUG_EVENT`/`EXIT_THREAD_DEBUG_EVENT` の登録先リスト決定）から呼ばれる。
- **`print_processes(dbg)`**: アクティブなプロセス（`dbg->pid`/`dbg->image_path`）とバックグラウンドリストの各プロセスを一覧表示する（`show processes` コマンド用）。アクティブなものには現在選択中である旨を付記する。
- **`free_all_processes(dbg)`**: バックグラウンドリストのノードのみを解放する（`debugger_restart`、4.2 節専用。`free_all_threads` と同じ方針）。

### 18.2 `do_process`（`process` コマンド）

`commands.c` の `do_process(dbg, arg)`: `strtoul(arg, NULL, 0)` で PID を解釈し、`switch_active_process()` を呼ぶ。成功した場合、切替先プロセスの `dbg->threads` の先頭（最初に判明しているスレッド）へ `dbg->tid`/`dbg->thread`/`dbg->locked_tid` を設定し（`thread <id>` コマンドが明示的な切替を「以後このスレッドを見続けたい」という意思表示とみなすのと同じ方針、17.3 節参照）、`switched to process id=<PID>, thread id=<TID> RIP=0x...` の形式で確認メッセージを表示する。切替先にまだ判明しているスレッドが 1 本もない場合は `switched to process id=<PID> (no known threads yet)` と表示する。指定 PID が見つからない場合は `no such process id=<PID>` と表示する。

### 18.3 フォーカス固定のプロセス間流用

プロセスをまたいだフォーカス固定専用の仕組みは実装していない。Windows のスレッド ID は生存中のプロセス間で重複しないため、`dbg->locked_tid`（17.3 節、スレッド単位の値）をそのまま使い回すだけで十分に成立する。すなわち、あるプロセスのあるスレッドにフォーカスが固定されている間、**別プロセス**の別スレッドが同種の停止要因（トラッキング済みブレークポイント／ウォッチポイント／ステップ着地）に遭遇した場合も、17.3 節で説明した「フォーカス外スレッドの自動継続」がそのまま適用される。5.2 節の `switch_active_process` 呼び出しが、この判定より前にアクティブプロセスを正しいものへ切り替えるため、`auto_continue` の判定式自体（`dbg->locked_tid != 0 && dbg->tid != dbg->locked_tid`）はプロセスをまたいでも一切変更する必要がなかった。

### 18.4 既知の制約

- **ブレークポイント・ウォッチポイントのプロセス間自動伝播は行わない**: 各プロセスの `breakpoints`/`watchpoints[4]` は完全に独立しており、親プロセスで設定したものが子プロセス（またはその逆）へ自動的に反映されることはない。子プロセス内の関数にも停止したい場合は `process <id>` で切り替えたうえで改めて `break`/`watch` を設定する必要がある（要件定義書 4.2 節参照。意図的な設計判断であり不具合ではない）。
- **子プロセスのシンボル初期化は一時的なアクティブ切替を伴う**: `CREATE_PROCESS_DEBUG_EVENT`（子プロセス分岐、5.1 節）は `SymInitialize`/`SymLoadModuleEx` を子プロセス自身のシンボルハンドルに対して行うため、登録直後に一時的に `switch_active_process()` でアクティブを切り替え、完了後に元のアクティブプロセスへ戻す。この間、ごく短時間ではあるが `debugger_t` の状態は子プロセスのものを指す。
