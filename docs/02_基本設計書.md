# 基本設計書

## 1. 概要

本ドキュメントは、`tdb`（Tiny Debugger）の基本設計を示すものです。
`tdb` は Windows 上で動作する小規模な CUI デバッガで、対象プログラムを
createprocess 経由で起動し、Win32 Debugging API と DbgHelp API を用いて
ブレークポイント、ステップ実行、式評価、メモリ・レジスタ・逆アセンブル表示、
メモリリーク追跡、停止時の PID/TID 表示などの機能を提供します。対象プログラム
がマルチスレッドの場合は、スレッドの生成・終了追跡、一覧表示、フォーカス
（対話コマンドの対象スレッド）の切替・自動固定にも対応します（v2.0）。対象
プログラムがさらに子プロセスを生成する場合は、その子プロセスも自動的に
追従デバッグし、プロセスの一覧表示・切替にも対応します（v3.0）。

## 5. モジュール設計

### 5.1 debugger_t 構造体

`debugger_t` はデバッガ全体の状態を保持します。主要メンバは下記の通り。

| メンバ | 用途 |
|--------|------|
| `process` / `thread` | 対象プロセスハンドル / フォーカス中のスレッドハンドル |
| `locked_tid` | フォーカス固定先の TID（0 = 未固定）。イベント発生元スレッドと一致しない場合、そのスレッドの停止は自動継続される（v2.0）。Windows のスレッド ID はプロセスをまたいで重複しないため、この仕組みはプロセスをまたいだフォーカス固定にもそのまま使える（v3.0） |
| `threads` | 生存中のスレッド一覧（`thread_entry_t` 連結リンクリスト、threads.c、v2.0）。常に「現在アクティブなプロセス」のスレッド一覧を指す |
| `processes` | 現在アクティブなプロセス **以外** の、追跡中の全プロセスの状態退避リスト（`process_entry_t` 連結リスト、processes.c、v3.0） |
| `pid` / `image_path` | 現在アクティブなプロセスの PID と実行ファイルパス（v3.0） |
| `sym_handle` | DbgHelp シンボルハンドル |
| `breakpoints` | ブレークポイントリンクリスト |
| `breakpoint_addr` / `original_byte` | 停止中のブレークポイント情報 |
| `temp_bp_addr` / `temp_bp_byte` | 一時ブレークポイント（up など） |
| `bp_rearm_addr` / `bp_rearm_byte` | 永久 BP の一時復帰後再有効化 |
| `next_mode` / `step_mode` | ステップ種別の判定フラグ |
| `list_file` / `list_next_line` | list コマンドの状態保持 |
| `target_program` | 対象プログラムパス（run 用） |
| `print_pretty` | 構造体/配列の整形表示フラグ |
| `leak_tracking` / `allocations` | リーク追跡の有効化と記録 |
| `watchpoints[4]` / `watch_count` | ハードウェアウォッチポイント配列と登録数 (watchpoints.c) |
| `calloc_addr` / `realloc_addr` | calloc/realloc のアドレスと元バイト |
| `current_alloc_func` | 現在の確保関数名（malloc/calloc/realloc） |

### 5.2 ブレークポイント制御

- 設定時に対象アドレスの先頭 1 バイトを `0xCC` (INT3) に書き換え、元バイトを保存。
- ヒット時は元バイトに戻し、1 命令実行後に `0xCC` を復元（rearm）。
- `si` / `step` / `n` / `up` は必要に応じて一時 BP またはトラップフラグを使用。

### 5.3 シンボル解決

- `SymInitialize` / `SymLoadModule64` を使用。
- `SymFromName` / `SymFromAddr` / `SymGetLineFromAddr64` / `SymGetTypeInfo` で
  名前・アドレス・行番号・型情報を取得。
- PDB がない場合は一部機能が制限される。

### 5.4 式評価（expr）

対応する式の例：

```
var
var.member
ptr->member
arr[i]
&var
*ptr
(type)expr
sizeof(type)
0x1234
'A'
expr + expr
```

演算子優先順位は C 言語に準じ、bison/flex で生成した文法（`expr_parser.y`/`expr_lexer.l`）で実装する。
各優先順位段を非終端記号として素直に積み上げた文法であり、旧実装（手書きの再帰下降パーサ）の各 `parse_XXX` 関数と 1 対 1 に対応する。
結果は `expr_val_t` に格納され、`is_lvalue` フラグでアドレス値か通常値かを区別。

キャストの結合順位は C 言語の単項式（unary-expression）レベルに合わせてあり、`(int)a + b` は
`((int)a) + b` として評価される。旧・再帰下降パーサではキャストのオペランドを式全体
（代入式レベル）まで貪欲に読み進めていたため `(int)(a + b)` 相当になっていたが、これは
文法の書き方に起因する意図しない挙動であったため、bison/flex 化に合わせて C 言語の意味論に
沿うよう修正した（詳細処理設計書 12 章参照）。

### 5.6 マルチスレッド管理（threads.c、v2.0）

- スレッド登録簿は `thread_entry_t {tid, handle, next}` の単方向連結リスト（先頭挿入）。`CREATE_PROCESS_DEBUG_EVENT`（起動時のメインスレッド）と `CREATE_THREAD_DEBUG_EVENT`（以降生成されるスレッド）でそれぞれ `register_thread()` を呼び登録する。`EXIT_THREAD_DEBUG_EVENT` で `unregister_thread()` により削除しハンドルを `CloseHandle`。
- `debugger_loop` は `EXCEPTION_DEBUG_EVENT` の先頭で毎回 `dbg->tid = ev.dwThreadId; dbg->thread = find_thread_handle(dbg, dbg->tid);` を実行し、そのイベントの発生元スレッドの実ハンドルへ正しく解決する（v1.x 時点では `dbg->thread` が起動時のメインスレッドのハンドルに固定されたままだった不具合の修正）。`CREATE_THREAD_DEBUG_EVENT`/`EXIT_THREAD_DEBUG_EVENT` 自体は `dbg->tid`/`dbg->thread` を変更しない（進行中の `step`/`next`/再武装シーケンスを乱さないため）。
- **フォーカス自動固定**: `debugger_t.locked_tid`（0 = 未固定）と現在のイベント元 `dbg->tid` を比較し、一致しない場合は当該イベントの表示処理を省略して自動継続する（`auto_continue` フラグ）。トラッキング済みブレークポイント・ウォッチポイント・ステップ着地の各分岐でのみ、実際に表示する際に `dbg->locked_tid = dbg->tid` を設定して固定する。未トラッキングのブレークポイントや Ctrl+C は固定のトリガーにしない。`thread <id>` コマンドは明示的に `locked_tid` を切替先へ更新する。固定中のスレッドが `EXIT_THREAD_DEBUG_EVENT` で終了した場合は `locked_tid` を 0 へ戻す。
- **ウォッチポイントの全スレッド適用**: DR0〜DR3/DR7 はスレッドごとの CPU レジスタであるため、`apply_watchpoints()`（watchpoints.c）は `dbg->threads` を走査して登録済みの全スレッドへ同じ設定を適用する（従来はフォーカス中のスレッドのみに設定していた）。新規スレッド生成時（`CREATE_THREAD_DEBUG_EVENT`）にも再適用し、後から生成されたスレッドにも既存のウォッチポイントが及ぶようにする。
- **ブレークポイント再武装中の他スレッド保護**: ソフトウェアブレークポイントの再武装（元バイトを一時的に復元してから 1 命令だけ実行し、`0xCC` を書き戻す）区間は、他のスレッドが同じ命令列を実行してヒットを見逃す競合状態を防ぐため、`suspend_other_threads()`/`resume_other_threads()` で他スレッドを一時停止する（対象: 恒久ブレークポイントの再武装、malloc/calloc/realloc/free エントリフックの再武装。詳細処理設計書 7.4 節・16.4 節参照）。この保護は継続的な `continue`/`step`/`next` 実行中には適用されないため、スレッド間で待ち合わせが発生するようなデッドロックのリスクは無い。

### 5.7 マルチプロセス管理（processes.c、v3.0）

- **「スワップ」方式**: `debugger_t` の各メンバ（`breakpoints`/`sym_handle`/`watchpoints`/`threads`/リーク追跡関連フィールド等、`5.1` 節参照）は、実装上は一貫して「現在アクティブなプロセス」のものだけを指す。子プロセスなど非アクティブな各プロセスの同じ情報一式は、新設の `process_entry_t`（`processes.c/h`）へまるごと退避しておく。この設計により、breakpoints.c/watchpoints.c/leakcheck.c/commands.c/symbols.c は「アクティブなプロセスを常に対象にする」という前提のまま一切変更せずに済む。
- **`switch_active_process(dbg, pid)`**: 現在の `debugger_t` の状態一式を新しい `process_entry_t` として `dbg->processes` へ退避し、切替先プロセスの `process_entry_t` を取り出して `debugger_t` へ復元、`dbg->pid`/`dbg->process` を更新する。`dbg->tid`/`dbg->thread` は意図的にクリアされたままにし、呼び出し元（`EXCEPTION_DEBUG_EVENT` 処理や `process <id>` コマンド）がそれぞれの文脈でフォーカスを再設定する。
- **プロセス登録・追跡**: `CREATE_PROCESS_DEBUG_EVENT` の発生元 PID がルートプロセスと異なる場合、`QueryFullProcessImageNameA` で実行ファイルパスを取得し、`register_new_process()` で新規の `process_entry_t` をバックグラウンドリストへ追加する（フォーカスは奪わない、スレッド生成時と同じ方針）。追加後は一時的に `switch_active_process()` でその子プロセスへ切り替え、専用のシンボルハンドルを初期化してからルートプロセスへ戻す。
- **プロセス終了処理（`unregister_process`）**: 終了したのが非アクティブなプロセスであれば、いったん `switch_active_process()` でそのプロセスをアクティブにしてから、通常の「アクティブプロセス終了」処理（ブレークポイント・リーク記録・スレッド一覧の解放、リーク未解放レポート表示）を行う。終了したプロセスにフォーカス固定（`locked_tid`）が向いていた場合は解除する。まだ他に追跡中のプロセスが残っていれば、その先頭を新しいアクティブプロセスへ昇格させ、`debugger_loop` を継続する。1 つも残っていなければ、従来通りデバッガ全体を終了する。
- **フォーカス固定の流用**: プロセスをまたいだフォーカス固定に専用の仕組みは設けていない。Windows のスレッド ID は生存中のプロセス間で重複しないため、`dbg->locked_tid`（スレッド単位の値）をそのまま使い回すだけで、「あるプロセスの特定スレッドに固定中、別プロセスの別スレッドが同種の停止要因に遭遇した場合は自動継続する」という 5.6 節の仕組みがプロセスをまたいでも自然に成立する。

## 7. 表示仕様

- `print_pretty` が on の場合、構造体/配列を複数行に展開して表示する。
- ポインタが `char*` / `unsigned char*` 系の場合、アドレスの後に文字列も表示する。
- `char` 型および 1 バイト整数は文字リテラル形式で表示する。
- `char` 配列は要素ごとに文字リテラル形式で表示する。
- `&` 演算子の結果はアドレスとして `0x...` 形式で表示し、元の型に `*` を付けた型名も表示する。
- ソースファイルが開けない場合やブレークポイント停止時、逆アセンブルを 1 行だけ表示する。
- `si` コマンド実行後も逆アセンブルを 1 行表示する。

## 8. 実行制御の拡張

### 8.1 Ctrl+C 転送

- デバッガが受け取った Ctrl+C を対象プロセスに転送し、実行を中断する。
- `DBG_CONTROL_C` (0x40010005) 例外を検出したらコマンドループに戻る。

### 8.2 アクセス違反の無視

- システム CRT 内で発生する `EXCEPTION_ACCESS_VIOLATION` (0xc0000005) は無視して実行を継続する。
- 例外情報は表示するが、ユーザー入力を待たずに自動的に再開する。

### 8.3 マルチスレッドイベントの自動継続（v2.0）

- `CREATE_THREAD_DEBUG_EVENT`/`EXIT_THREAD_DEBUG_EVENT` は生成・終了メッセージのみ表示し、コマンドループには入らず自動的に実行を継続する。
- フォーカス固定中（`locked_tid != 0`）にフォーカス外のスレッドがトラッキング済みブレークポイント／ウォッチポイント／ステップ着地に遭遇した場合も、詳細表示・コマンドループ突入を省略し、1 行の通知（例: `thread id=1234 hit breakpoint at 0x... (not focused, continuing)`）のみを表示して自動的に実行を継続する。

### 8.4 マルチプロセスイベントの自動継続（v3.0）

- `CREATE_PROCESS_DEBUG_EVENT`（ルートプロセス以外、つまり子プロセス）は生成メッセージのみ表示し、コマンドループには入らず自動的に実行を継続する。フォーカスも奪わない。
- `EXCEPTION_DEBUG_EVENT` の発生元プロセスが現在アクティブなプロセスと異なる場合、詳細処理に入る前に `switch_active_process()` でアクティブプロセスを切り替える。これにより、ブレークポイント判定・ウォッチポイント判定・フォーカス自動固定判定など、既存のスレッド向け処理がそのまま「切替後のプロセスの」処理として正しく動作する。
- `EXIT_PROCESS_DEBUG_EVENT` は、それがルートプロセスであり、かつ他に追跡中のプロセスが残っていない場合にのみデバッガ全体を終了する。子プロセスの終了、またはルートプロセスの終了後も他プロセスが残っている場合は、終了メッセージのみ表示してコマンドループには入らず `debugger_loop` を継続する。
